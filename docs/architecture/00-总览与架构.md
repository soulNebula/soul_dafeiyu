## 一、先把「训练」这件事说清楚

你说「想通过这些文件去训练大模型」。这里有一条必须先掰明白的岔路，否则后面全白做。

**大模型有两种「学」：**

| 路径 | 做法 | 学到什么 | 能不能记住用户 | 成本 | 是否可删可查 |
|---|---|---|---|---|---|
| A · 不改权重 | 检索增强 + 记忆文件 + 提示词 | 事实、偏好、经历、说话方式 | ✅ 能 | 低（只要 API 费） | ✅ 每条可删、可查、可改 |
| B · 轻量微调（LoRA/SFT） | 用几万条聊天记录训练 | **只学到「腔调」** | ❌ 记不住具体的人 | 高（显卡 + 数据工程） | ❌ 不可查、不可删、会串味 |
| C · 偏好学习（DPO） | 打分数据 → 偏好对 | 判断「哪种回复更好」 | ❌ | 很高 | ❌ |

**对这个项目，结论很明确：**

1. **记住用户这件事，微调是最差的手段。** 微调把信息压进权重，你没法知道它记住了什么、记错了什么、删不掉、换个人还会串。你上次问的「怎么防幻觉」，在微调路线下是无解的——因为你连「它根据什么说的」都查不到。
2. **微调唯一值得做的地方，是「说话腔调」。** 如果你想让 AI 的口吻接近某个人的语感，B 路线可以做，但那是最后一步的锦上添花，不是地基。
3. **所以 v1 全是 A 路线：** 模型不动，把所有成长做进外部系统。等 A 跑顺了、有了几万条「好/坏回复」的打分数据，再考虑 C。

> 一句话：**你要造的不是「训练流程」，是「记忆与人格的运行时」。**

## 二、能力边界：能做到什么，做不到什么

### 能做（且有工程路径）

| 能力 | 实现方式 | 难度 |
|---|---|---|
| 记住每个用户说过的事 | 结构化记忆 + 证据指针 | ★★ |
| 认识用户的性格、作息 | 画像蒸馏 | ★★★ |
| 形成稳定、不漂移的人格 | 人格分层 + 版本控制 | ★★ |
| 越聊越会聊 | 策略变体 + 打分 + 灰度 | ★★★★ |
| 看懂朋友圈图片/视频/表情包 | 本地 VLM + OCR + ASR | ★★★ |
| 理解用户的弦外之音 | 情绪/意图标注 + 检索同类历史 | ★★★ |
| 主动关心（隔天回访） | 心跳 + 目标树 | ★★ |

### 做不到（别承诺，也别花钱试）

| 幻想 | 现实 |
|---|---|
| 它自己悟出因果 | 不会。因果必须外化成「情境-行动-结果」三元组 |
| 聊得越多越聪明（通用能力） | 不会。只会越来越「懂这个用户」 |
| 无监督自我进化 | 会退化成自恋 + 幻觉自我强化 |
| 靠朋友圈数据「训练」出人格 | 朋友圈给的是**素材**，人格要靠策略和反馈长出来 |
| 一次配置，永久有效 | 人格会漂移，必须限速 + 审计 |

## 三、与 wx_box 已有模块的对接

这是本设计最重要的一节：**不重造轮子**。现有代码已经解决了最脏最累的活。

| 现有模块 | 提供什么 | 本系统怎么用 |
|---|---|---|
| `wx_core/db_source.py` | 只读解密 + WAL 叠加 + 增量轮询，产出 `Message` | **唯一的消息来源**，不重复实现 |
| `wx_core/models.py` | `Message(friend, kind, sender, text, media_path, extra, ts, id)` | 学习层的输入结构，建议只加字段不改字段 |
| `log/messages.jsonl` | 全量结构化归档，一行一条 | 离线管线的输入源（可重放、可回溯） |
| `media/originals/`、`media/stickers/` | 图片/表情包原件（含 GIF、wxgf→GIF） | 媒体理解的输入 |
| `wx_core/ocr.py` | 本地 RapidOCR / Windows OCR 双通道 | **图片文字提取直接复用**，不用再引 PaddleOCR |
| `wx_core/emoticon.py` | 表情包识别、wxgf 处理 | 表情包管线的基础 |
| `WechatMoments/` + `_tmp_moments.json` | 朋友圈 `{id, author, create_time, content, location, media[]}` | 朋友圈理解的输入 |
| `tools/search_messages.py` | 关键词/时间/联系人检索 | 检索的**基线实现**，记忆检索先用它跑通 |
| `tools/export_emoticons.py` | 表情包库导出 + manifest | 建「表情包人格档案」 |
| `docs/风控与合规说明.md` | 合规基线 | 本设计的合规章节直接引用 |
| `web_app.py` / `app.py` | 本地网页 + 桌面 UI | 后续加「记忆浏览器 / 画像面板 / 提案审核」页 |

### 需要给 `Message` 补的字段（建议，不破坏兼容）

```python
conv_id: str = ""      # 会话唯一 id（群聊需要，好友可用 wxid）
quote_id: str = ""     # 引用的消息 id（微信「回复」）
reply_to: str = ""     # 被回复的消息 id
is_group: bool = False
sender_wxid: str = ""  # 群聊里区分具体发言人
```

> 没有 `sender_wxid`，群聊的「谁说的」就永远是错的，画像会直接串味。

## 四、架构：五层

```
┌─────────────────────────────────────────────────────────────┐
│ L1 采集层（已有 · wx_box）                                     │
│   db_source → Message → log/messages.jsonl + media/          │
│   WechatMoments → moments                                    │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ L2 理解层（新 · agi/understand）                               │
│   媒体理解：图片/视频/表情包 → caption + tags + emotion        │
│   文本切段：会话切分 → 话题段                                 │
│   抽取：claim / 事件 / 偏好 / 关系 / 因果候选                  │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ L3 记忆层（新 · agi/memory）   ← 全系统最该先钉死的地方         │
│   episodic（原始）→ semantic（画像）→ correction（纠正）       │
│   写入闸门：证据指针 / 来源分级 / 冲突检测 / 脱敏              │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ L4 决策层（新 · agi/brain）                                    │
│   检索 → 策略生成（技能先验+变体采样）→ 规划 → 工具            │
│   回复生成 → 引用校验 → 降级                                  │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│ L5 学习层（新 · agi/learn）                                    │
│   打分（显式/隐式/延迟/裁判）→ 变体统计 → 反思 → 提案 → 灰度   │
└─────────────────────────────────────────────────────────────┘
```

**关键：L5 的输出只能改 L3 的「人格/技能/策略统计」，永远不能直接改 L1 的原始数据。**

## 五、端到端走一遍（一次完整的「学到」）

以「用户在朋友圈发了张加班的图」为例：

| 步 | 发生什么 | 落盘 |
|---|---|---|
| 1 | 朋友圈同步，拿到 `{author, content:"又是凌晨", media:[加班照片]}` | `moments.jsonl` |
| 2 | 图片走理解管线 → `caption:"深夜办公室，桌上两杯咖啡，屏幕亮着"` | `media_annotation` |
| 3 | 抽 claim：`用户近期加班频繁`（证据：该条朋友圈 + 3 天前聊天"今晚要改方案"） | `mem_episodic` × 2 |
| 4 | 画像蒸馏：`近期状态=高压/过劳`，置信 0.72，支持 4 条证据 | `mem_semantic` |
| 5 | 三天后用户发「累」，检索命中「高压/过劳」+ 历史「加班」 | 上下文 |
| 6 | 策略：共情优先、不建议、不追问工作 → 回复 | `turns` |
| 7 | 用户连回 3 条，情绪值 -0.7 → -0.3 → 打分 0.78 | `turns.score` |
| 8 | 当晚反思：该策略在本情境胜出 → 变体统计 +1 | `skill_variant` |

**这条链上，任何一步没有证据指针，就断在那里，不许往下走。**

```
│   ├── causal/              M12

│   ├── learn/                M17 M18 M19
│   ├── scheduler/            M20
│   └── data/                 ← 所有落盘数据（gitignore）
│       ├── raw/              原始归档（软链到 ../log 和 ../media）
│       ├── db/               sqlite 主库
│       ├── media_index/      媒体标注结果
│       ├── memory/           记忆 md 快照（人可读）
│       ├── persona/          人格文件（人可读）
│       └── proposals/        待审提案
├── log/                      ← 已有
├── media/                    ← 已有
└── WechatMoments/            ← 已有
```

**双写原则：** 每条重要数据既进 SQLite（查询快），又落一份 `.md`/`.jsonl`（人可读、可 diff、可手工修）。线上排查靠 md，机器检索靠 db。

## 八、关键设计决策（拍板表）

| # | 决策 | 结论 | 理由 | 可逆 |
|---|---|---|---|---|
| D1 | 是否微调 | **v1 不做** | 记住人只能靠 RAG | 可逆 |
| D2 | 存储 | SQLite + md 双写 | 单机、零运维、可 diff | 可逆 |
| D3 | 嵌入 | 本地 embedding（如 bge-small-zh） | 隐私不出机 | 可逆 |
| D4 | VLM | 本地优先，云端需脱敏白名单 | 朋友圈是敏感数据 | 可逆 |
| D5 | 发送能力 | **一期不做** | 见 05 风险登记册 R1 | 可逆 |
| D6 | 记忆写入 | 必须过闸门，pending 人工/规则复核 | 防污染闭环 | 不可逆（必须） |
| D7 | 人格 core | 只有人能改 | 防漂移 | 不可逆（必须） |

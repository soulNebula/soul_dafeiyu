# 14 · 按需运行与唤醒机制

> ⚠️ **设计依据文档，非施工图。实施以 [PLAN.md](PLAN.md) 为准；冲突时一律以 PLAN 为准。**


> 你的想法：**不要让 LLM 按固定循环跑，要让它「觉得该跑的时候才跑」，并且用户有按钮能终止。**
> 这个方向是对的，但里面有一个必须先解决的悖论。这份文档给出优化后的方案。

---

## 一、你的直觉对在哪

固定循环（每 30 分钟跑一次）有三个硬伤：

| 问题 | 表现 |
|---|---|
| **烧钱** | 一天 48 次 × 每个用户，99% 的时候没事可做 |
| **机械感** | 「到点说话」，和 11 文档里说的营销号是同一个病 |
| **KPI 化** | 为了「证明自己活着」而做事，不是真有事 |

**所以「按需运行」是对的方向。**

---

## 二、但有一个悖论：谁来唤醒守夜人

> **一个没在运行的程序，没法决定自己什么时候运行。**

如果「什么时候醒」完全交给 LLM 判断，那它得先醒着才能判断——死循环。

### 解法：**唤醒 ≠ 运行**

把这个词拆成两件事：

```
唤醒（wake）   = 看一眼有没有事     → 便宜，可以一直做
运行（think）  = 真的动脑子          → 贵，只在必要时做

让便宜的东西一直醒着，让贵的东西被叫醒。
```

这其实就是人的工作方式：**感官一直在低功耗运行，但「专注思考」是稀缺的、被触发的。**

---

## 三、三段式架构

```
┌──────────────────────────────────────────────────────┐
│ L0 · Ticker（常驻，零 LLM）                            │
│   每 30 秒看一眼：有新消息吗？有到点的意图吗？          │
│   成本 ≈ 0（就是一次数据库查询）                        │
└────────────────────┬─────────────────────────────────┘
                     ▼ 有事才往下走
┌──────────────────────────────────────────────────────┐
│ L1 · Gatekeeper（规则 + 小模型，毫秒级，极便宜）        │
│   这事值得叫醒大脑吗？优先级多少？预算够吗？            │
│   90% 的事情在这里被过滤掉                              │
└────────────────────┬─────────────────────────────────┘
                     ▼ 通过了才叫
┌──────────────────────────────────────────────────────┐
│ L2 · Brain（LLM，贵，秒级）                            │
│   真正思考：要不要做、怎么做、做完排下次                │
└──────────────────────────────────────────────────────┘
```

| 层 | 成本 | 频率 | 职责 |
|---|---|---|---|
| L0 | ≈ 0 | 每 30 秒 | 只做「有没有变化」的检查 |
| L1 | 微秒–毫秒 | 有变化时 | 过滤、排序、预算检查 |
| L2 | 钱 + 秒 | **一天 3–20 次** | 真思考 |

**这就是「按需运行」的正确实现**：不是它自己决定醒不醒，是**便宜的守夜人替它盯着，值钱的事才叫它。**

---

## 四、核心机制：自我调度（self-scheduling）

这是解决悖论最漂亮的一招。

**它不能说「我三小时后再醒」，但它可以说「三小时后提醒我看看他面试结果」——然后写进队列。**

```yaml
# intent_queue 一条
id: I-20260118-014
kind: follow_up          # follow_up | share | check | reflect | learn
reason: "用户说周三面试，今天周四，该问问结果"
wake_at: 2026-01-19T20:00 # ← 它自己定的时间
priority: 0.7
cost_estimate: 1         # 预计消耗 1 次 brain 调用
expires_at: 2026-01-21T00:00
status: pending
```

于是：

```
它这次醒来
  → 想：这件事三天后要跟进
  → 写一条 intent，wake_at = 三天后
  → 睡去
三天后
  → Ticker 发现 intent 到点
  → Gatekeeper 放行
  → 它被自己的计划叫醒
```

**「什么时候运行」就真的变成它的决定了**——只不过这个决定是在它上一次清醒时做出的。

> 这是整套设计里我最喜欢的一处：**用「写待办」代替「设定时器」**，
> 既保留了自主性，又不需要它一直醒着。

---

## 五、触发源：只认「状态变化」，不认「时间流逝」

| 触发类型 | 例子 | 优先级 | 说明 |
|---|---|---|---|
| **用户消息** | 有人发来消息 | **1.0（最高，永远放行）** | 绝不排队 |
| **承诺到期** | 「明天问问面试结果」 | 0.8 | 它自己排的 |
| **内部需求** | 分享欲 drive ≥ 0.75 | 0.5–0.7 | 见 11 文档 |
| **冲突未解决** | 记忆里有条冲突挂着 | 0.6 | 见 02 文档 |
| **学习任务** | 有个技能卡在 level 1 | 0.3 | 闲时做 |
| **时间兜底** | 24 小时没醒过 | 0.4 | **防假死，见第七节** |

**关键区别：**

- ❌「每 30 分钟跑一次」→ 时间是触发源
- ✅「有人说话了 / 承诺到点了 / 憋不住想分享了」→ **状态变化**是触发源

**时间只在两种情况下出现：作为「截止时间」和「兜底」，不作为「发车时刻」。**

## 六、能量预算（防暴走）

人一天能专注思考的次数是有限的。系统也该有。

```yaml
budget:
  daily_brain_calls: 20      # 每天最多叫醒大脑 20 次
  daily_tokens: 200000
  per_hour_calls: 5
```

规则：

| 情况 | 处理 |
|---|---|
| 预算充足 | 按优先级正常放行 |
| 预算剩余 < 20% | 只放行优先级 ≥ 0.7 的 |
| 预算耗尽 | **只放行用户消息**，其他全部顺延到明天 |
| 连续 3 天耗尽 | 报警：说明阈值设错了，或它在瞎忙 |

**这条比任何「不要打扰用户」的规则都有效**——因为它限制的是**它自己瞎折腾的能力**。

---

## 七、防假死：兜底心跳

事件驱动最大的风险是**再也不醒**。

| 兜底规则 | 值 |
|---|---|
| 最长静默 | **24 小时必醒一次**（即使无事可做） |
| 兜底时做什么 | 极低成本自检：有无到点承诺、有无未解决冲突、预算是否正常 |
| 兜底后仍无事 | 写一条日志，继续睡（**不要为了刷存在感发消息**） |

**兜底唤醒 ≠ 兜底发言。** 醒了看一眼没事，就继续睡。这是两件事。

---

## 八、开关：五级（你要的那个按钮）

**一个「停止」按钮不够用。** 要分级，因为不同场景需求不同：

| 级别 | 名称 | 效果 | 恢复方式 |
|---|---|---|---|
| **S0** | 完全停机 | 进程退出，不回复、不记录 | 手动启动 |
| **S1** | 只回消息 | 关闭一切主动行为，但回复照常 | 手动 / 24h 后询问 |
| **S2** | 暂停 24h | 连回复也停，消息排队 | 到期自动恢复 + 告知 |
| **S3** | 单次否决 | 「这次别想了」——丢弃当前 intent | 一次性 |
| **S4** | 静默观察 | 只记录不行动（调试用） | 手动 |

### 三条硬要求

1. **响应必须 < 1 秒。** 用户按了停，就要立刻停——**不能等它「思考完这一轮」。**
2. **状态永远可见。** 界面上必须有：
   ```
   ● 运行中（上次唤醒 32 分钟前：回复消息）
   ○ 已暂停（今日 21:40 恢复）
   ```
3. **恢复要告知。** 不能静默恢复——「我回来了」比「悄悄又开始发消息」体验好十倍。

## 九、可解释性面板（信任的来源）

用户最怕的不是它自己跑，是**不知道它在跑什么**。

```
┌─ 它现在在做什么 ────────────────────┐
│ 状态：休眠中                        │
│ 下次唤醒：今天 20:00（跟进面试结果） │
│                                     │
│ 最近 5 次唤醒：                     │
│  09:12  用户消息（回复）            │
│  08:00  兜底自检（无事，继续睡）    │
│  昨天 21:30 分享（他看到一条帖子）  │
│                                     │
│ 今日预算：7/20 次                  │
│ 待办队列：2 条                     │
└─────────────────────────────────────┘
```

**这个面板是「自主性」和「失控感」之间的那道墙。**
没有它，用户会觉得系统在偷偷做决定；有了它，用户会觉得「它有自己的安排，但我看得见」。

## 十、数据表

```sql
CREATE TABLE intent_queue(
  id TEXT PRIMARY KEY,
  subject TEXT,
  kind TEXT,               -- follow_up|share|check|reflect|learn
  reason TEXT NOT NULL,    -- 为什么要做（人能看懂）
  wake_at REAL,            -- 它自己定的时间
  priority REAL,
  cost_estimate REAL,
  expires_at REAL,
  status TEXT DEFAULT 'pending',  -- pending|done|dropped|expired
  created_at REAL
);

CREATE TABLE wake_event(
  id TEXT PRIMARY KEY,
  ts REAL,
  trigger TEXT,            -- user_msg|intent_due|drive|fallback|manual
  intent_id TEXT,
  gate_result TEXT,        -- passed|filtered|budget_blocked
  brain_called INTEGER,
  cost_tokens INTEGER,
  note TEXT
);

CREATE TABLE switch_state(
  subject TEXT PRIMARY KEY,
  level TEXT DEFAULT 'S1',
  changed_at REAL,
  resume_at REAL,
  changed_by TEXT
);
```

## 十二、验收指标

| 指标 | 目标 |
|---|---|
| 每日 brain 调用次数 | 3–20 次（**显著低于固定循环的 48 次**） |
| 唤醒后「做成了事」的比例 | ≥ 60%（低于 40% 说明 Gatekeeper 太松） |
| 假死检测（>24h 无唤醒） | 0 |
| 开关响应延迟 | < 1s |
| 预算超支天数 | < 5% |
| 静默恢复（未告知） | 0 |
| 用户主动关闭后又被唤醒 | **0** |

---

## 十三、一句话总结

> **不要让它「一直在跑」，也不要让它「自己决定什么时候醒」——**
> **让便宜的东西一直醒着，让贵的东西被叫醒。**
>
> 它真正的自主性不体现在「什么时候启动」，
> 而体现在**「醒着的时候，它决定给自己排什么活」**。

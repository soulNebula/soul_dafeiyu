## 一、为什么做 W3

W2 的结论是「内状态层不达标、默认 off、暂不做 LoRA」。但那次实验暴露了两个基础设施缺口：

1. **不知道慢在哪**：`turns` 表没有延迟字段，W2 用的 6.0s 中位数来自日志文本，无法按模式/轮次切片。
2. **收不到偏好信号**：反馈只有 good/ok/bad 三个按钮，且同一轮可被重复记多条（基线实测 6 行覆盖 5 轮），无法回答「为什么好/为什么差」，也没有 A/B 配对采集口。

W4 要做小模型蒸馏，这两个缺口必须先补：延迟决定「2B 小模型值不值得上」，偏好数据决定「谁来判模型好不好」。

## 三、关键设计

### 1. 延迟的语义边界

`latency_ms` = `send()` 入口 → 写 turn 的耗时，**包含**模型调用、检索、记忆读写，**不含**微信实际发送。

这么做是为了可比：所有模式（off/static/rule/model/shadow）都在同一条路径上埋点，切换模式后数字可直接对比。若把发送也算进去，微信端网络抖动会污染结论。

### 2. shadow 模式的取值

同一轮里，shadow 用 `agi/inner/inject.build_inner_ctx(..., "rule", ...)` 渲染，落库的 `block` 与 rule 臂**同源**——这样离线就能回答「如果当初注入，会注入什么」，不需要重放。

但它有一个硬约束，且已用测试锁死：`INNER_MODE=shadow` 时 `inner_ctx=""`，prompt 与 `off` 逐字节相同。**只记录，不改变行为。**

### 3. 反馈幂等

原实现是「插一条新的」，同一轮点两次 good→bad 会留两行，对账时 `turns.feedback` 与 `feedback` 表对不上。

改成先删后插的语义（同一 `turn_id` 只保留最新一次判断）后：

- 重复点同一按钮 → 行数不变；
- 改判 → 1 行，值等于最后一次；
- `turns.feedback` 同步更新，对账一致率 100%。

### 4. pairwise 是什么

`pairs` 表存的是「同一上下文下，两条回复谁更好」：`turn_a/reply_a/model_a` + `turn_b/reply_b/model_b` + `choice ∈ {a,b,tie}` + `context_json`。

W2 的盲评是离线一次性跑出来的 CSV；W3 之后这条通道变成**在线**的：网页上可以随时发一对、点一下、落库。W4 的本地 2B vs 教师对比，就靠这条通道攒真实偏好，而不是只靠我人工看 50 条。

## 四、实测与现状

### 全量测试

python -m pytest agi/tests -q
→ 678 passed in 229.75s（W2 合并时 645，W3 净增 33 项）

### 线上库迁移未发生（正常）

查 `agi/data/selflearn/selflearn.sqlite3`：`turns` 66 行、**无 `latency_ms` 列**，`pairs`/`inner_states` 表不存在。

原因：迁移写在 `db.connect()` 里，而机器人进程从 W3 合并后还没重启过。**下次启动会自动 `ALTER TABLE` 补列**，不需要手工迁移脚本。这也意味着：W3 之后的延迟数据从「重启那一刻」开始积累，之前的历史轮次永远是 NULL，不要拿 NULL 当 0 算均值。

### 已知限制

| 限制 | 影响 | 处理 |
|---|---|---|
| 延迟不含真实发送 | 与用户体感有 0.1–0.3s 差 | 文档写明；对外只说「生成侧延迟」 |
| shadow 只记 rule 渲染 | 看不到 model 臂的 shadow 样子 | 够用：rule 是 model 的回退基线 |
| pairwise 无 UI 入口操作面板 | 目前只有 API | W4 盲评时用脚本批量灌，不阻塞 |
| 原因标签是固定 4 个 | 覆盖不全 | 先积累分布，再决定是否加自由文本 |

## 五、对 W4 的意义

1. **延迟基线**：2B LoRA 上线后，`latency_ms` 的 P50/P95 可以直接和 DeepSeek 版本对比，判断「灵魂线」是否把响应拖慢。
2. **偏好数据管道**：`pairs` 表 + `/api/pairwise` 是 W4「本地 vs 教师」盲评的落库口；没有它，盲评结果只能停在 CSV。
3. **shadow 快照**：`inner_states` 里已经有 rule 渲染的状态块，将来可以拿它和 2B 模型输出的 JSON 做逐字段对比，作为一致性门槛（≥80%）的第一版测量。

## 一、为什么走这条线

W2 的四臂消融结论很硬：**prompt 里塞一段内状态，对回复质量没有可测提升**（`rule:off` 35.3%，置信区间 21.5–52.1，跨不过 50%）。这说明"灵魂"不是加一段文字就能长出来的——DeepSeek 读到"你现在 mood=0.4"并不会真的换一种说话方式，它只是在扮演。

所以 W4 换了个问法：**不要求大模型"扮演"状态，而是让一个小模型专门负责"判断状态、决定表现"，把判断结果作为硬指令交给大模型**。

- 小模型（Qwen3.5-2B + LoRA）：输入 = 人格 + 当前状态向量 + 最近几轮 + 用户这句话 → 输出 = `InnerState` JSON（stance / intent / monologue / behavior）
- 大模型（DeepSeek）：只负责"把话说好"，收到的是一段行为指令，不再自己揣摩情绪
- 记忆/状态机：仍然由 `agi/selflearn` 管，和 W3 一样记录、演化

一句话：**灵魂从"提示词"变成"一个小模型的权重"。**

## 二、数据

### 形态

每行 = `{id, source, state_profile, context, user_msg, target(InnerState), teacher, split, ts}`。

teacher 是 DeepSeek，温度 0.2、max_tokens 300，输出严格 JSON，用 `agi/inner/schema.py` 校验；失败重试 1 次，仍失败丢弃并计数。

### 真实数据的天花板（W4-A 实测）

| 来源 | 数量 |
|---|---|
| golden_v1 唯一 user_msg | 50 |
| `log/messages.jsonl` 质量过滤后唯一 user_msg | 63 |
| 真实侧唯一 user_msg 合计 | **113**（硬天花板） |
| 去重后唯一 context 窗口 | 131 |

这就是为什么 v1 需要"真实 context × 7 个 state_profile"的放大：同一句话在不同状态下，**正确表现本来就不同**（该追问 vs 该闭嘴、该接梗 vs 该正经），所以 7 个 profile 是 7 个不同样本，不是复制。

### 目标规模

| 部分 | 行数 | 说明 |
|---|---|---|
| 真实 context × 7 profile | 1267 | golden 50 + messages 131 窗口，每窗口 7 个状态 |
| synthetic | 733（36.7%） | 10 桶各 ≥60，口语化，unique user_msg ≥600 |
| 合计 | **2000** | unique_user_msg ≈ 846；max_dup ≤ 7（且 profile 不同） |

成本：约 **¥2.7**（teacher 调用 2000 次，实测 300 条 ¥0.41）。

### 两条数据红线

1. **验证 teacher 真的看 profile**：抽 20 个 context × 7 profile，比较 `(stance, intent, length, ask, emoji)` 签名，要求 ≥80% 的 context 产出 ≥3 种签名。达不到就说明 7× 是假多样性，必须缩到 4 个 profile 并用 synthetic 补。
2. **切分按 context 哈希**，同一 context 的所有 profile 变体必须在同一侧；val 取 20% context，且每个 context 保留 default-profile 行供门槛评估。

## 三、训练（6GB 显存实测）

### 环境

全部在 `E:\agent`（E 盘 227G 空闲；C 盘只剩 23G）：

```
E:\agent\venv312\            Python 3.12.6
E:\agent\models\Qwen3.5-2B\  Qwen3.5-2B 多模态（4.55GB，632 tensors）
E:\agent\cache\{pip,modelscope,wheelhouse}
E:\agent\output\             adapter
E:\agent\logs\               smoke 日志
```

版本：torch 2.6.0+cu124 / transformers 5.20.2 / peft 0.21.2 / accelerate 1.15.0 / datasets 5.1.0 / bitsandbytes 0.50.2（已装未用）。

### smoke 实测（20 步，bf16 LoRA）

参数：r16 / α32 / dropout 0.05 / seq512 / bs1 / grad ckpt / 视觉塔 offload CPU。

| 指标 | 结果 |
|---|---|
| 步数 | 20/20，无 OOM、无 NaN |
| 耗时 | 首轮 27.16s（1.36s/step），复跑 25.16s（1.26s/step） |
| loss | 2.2534 → 0.9025（复跑 0.9139），可重跑一致 |
| 峰值显存 | nvidia-smi **5849/6141 MiB = 5.71GB**；torch reserved 5.578GB |
| 可训练参数 | 16.82M（372 个 LoRA 模块） |
| 权重占用 | 加载 4.123GB → 视觉塔挪 CPU 后 3.505GB → 注入 LoRA 后 3.568GB |
| adapter | `E:\agent\output\smoke_adapter`（67MB） |
| 降级验证 | seq256 峰值 reserved 4.885GB（余量翻倍） |

**结论：6GB 能训 2B LoRA，但余量只有 ~292MiB，必须遵守三条**——seq ≤512、grad ckpt 必开、视觉塔必须 offload。

### 长篇训练暴露的真问题：Windows 显存碎片

20 步 smoke（ga1）峰值 reserved 稳定在 5.578GB。但换成 v0 全量 300 步后：

| 配置 | 峰值 reserved | 现象 |
|---|---|---|
| ga8（8 微批/步） | **6.838GB** | 第 4 步起越过 6GB，spill 到系统内存，单步从 10.4s 涨到 13.3s |
| ga1（1 微批/步） | **11.041GB** | 单步 1.31s（速度没掉，但 5GB 权重+激活被塞进系统内存，危险） |

根因：Windows 上 PyTorch 的 `expandable_segments` **不可用**，而样本长度在 234–341 token 间变化，caching allocator 每步切新块、旧块不回收，reserved 一路涨。

处置（已写进脚本）：

1. **长度分桶排序**（`--sort-chunk 64`）：打乱后每 64 条按长度排序；
2. **batch 长度量化**（`--pad-bucket 64`）：padding 对齐到 64 的倍数，块尺寸收敛到少数几档，可复用；
3. **allocator 参数**：`PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:64,garbage_collection_threshold:0.9`；
4. 备用 `--empty-cache-every N`（碎片仍严重时周期性 `empty_cache()`）。

**教训**：smoke 只跑 20 步看不出碎片问题——短跑不能当稳定性证据。以后任何"能跑"的结论都要跑到 ≥1 个 epoch 再下。

### 更要命的发现：推理慢在 CPU，不在 GPU

训练修好后，评测结果暴露了比显存更根本的问题——**本地推理太慢，慢到不能同步用**。

单条评估（同一 prompt，128 token 输出，贪心）：

| 模型 | 单条耗时 | 输出 token | 有效速度 |
|---|---|---|---|
| Qwen3.5-2B（bf16） | **15.92s** | ~127 | ≈8 tok/s |
| Qwen2.5-0.5B + LoRA（bf16） | **12.64s** | ~128 | ≈10 tok/s |
| Qwen2.5-0.5B（base，只回一句） | 0.75s | 短 | — |

参数量差 4 倍，耗时只差 1.26 倍 → **瓶颈不是权重、不是显存、不是算力**。

进一步实测：
- 单步 forward（带 KV cache）：0.5B 约 45ms/token，bf16 / fp16 / fp32 **几乎一样**（46.8 / 44.3 / 49.1ms）。如果是显存带宽瓶颈，fp32 会慢一倍——没有，说明卡在 **CPU 侧的 Python/算子调度开销**。
- `torch.compile`：装了 triton-windows（3.2.0 对应 torch 2.6），但 inductor 生成代码报 `NameError: name 'torch' is not defined`，`suppress_errors` 后静默回退 eager，**零加速**。
- 这台机器：Ryzen 7 7735H（系统报 4C/8T）、16GB 内存、驱动 616.92。

**对路线的影响**：按原设计「每轮先跑小模型出状态，再让大模型回话」，光小模型就要 13–16 秒，叠加 DeepSeek 的 6 秒 → 单轮 20 秒，不可用。

三条出路（正在验证，按优先级）：

| 方案 | 做法 | 预期 | 代价 |
|---|---|---|---|
| A. 换推理栈 | llama.cpp + GGUF（Q4），不走 HF/Python | 0.5B 可达 100+ tok/s，128 token ≈1s | 需要 adapter 合并 + 转 GGUF 的流水线 |
| B. 压缩输出 | target 从 128 token 压到 ~65（短键名），再压到 ~20（只出 behavior） | 65 tok ≈3s；20 tok ≈1s | 丢失完整独白，stance/intent 回退 rule |
| C. 异步 | 小模型在回复发出后后台算，下一轮生效 | 用户零延迟 | 状态慢一拍，突发情况反应迟 |

**重要**：数据是模型无关的（`(状态+上下文)→InnerState JSON`），换底座（2B→0.5B→GGUF）**不需要重做数据集**。

### 已验证的解法：llama.cpp + GGUF

同一台机器、同一个 0.5B 模型，换 llama.cpp（GGUF Q4_K_M，`-ngl 99`，CUDA 后端）实测：

| 栈 | prompt eval | 生成速度 | 128 token 耗时 |
|---|---|---|---|
| HF + Python（torch eager） | ~60 tok/s | **≈9–12 tok/s** | 12.6s（0.5B）/ 15.9s（2B） |
| llama.cpp + GGUF Q4（Optimus 混合输出） | 1251 tok/s | **124.9 tok/s** | **≈1.0s** |
| llama.cpp + GGUF Q4（**开独显直连 MUX 之后**） | 866 tok/s | **282.4 tok/s** | **≈0.45s** |

**提速 23–28 倍**（相对 HF）。MUX 开启后又快 2.3 倍——说明之前有相当一部分时间耗在 Optimus 的跨 GPU 拷贝上，不只是 Python 开销。**「开独显直连」要写进部署要求**。

而且：
- 显存只占几百 MB（Q4 权重 0.49GB），6GB 卡再也不紧；
- llama-server 支持 JSON schema / grammar 约束输出 → G1 合法率可做到 100%（由解码器保证，不靠模型自觉）；
- 附带好处：不再受 torch/transformers 版本、多模态视觉塔、Windows 显存碎片这些问题影响。

代价是新增一条部署链路：**peft adapter → merge 成 HF → 转 f16 GGUF → 量化 Q4_K_M → llama-server**（W4-E 任务），以及把客户端从 HF 换成 HTTP。

**这改变了「2B 还是 0.5B」的结论**：原以为 2B 太大、6GB 装不下训练，所以只能 2B bf16；现在推理侧 GGUF Q4 让 2B（1.3–1.5GB Q4）也完全放得下，速度约 60–80 tok/s（≈1.6–2s/128token），是「质量换速度」的可选档。

补充实测（同一 prompt、128 token、Q4_K_M、`-ngl 99`）：

| 底座 | Q4 大小 | prompt eval | 生成速度 |
|---|---|---|---|
| Qwen2.5-0.5B-Instruct | 0.49GB | 1251 tok/s | **124.9 tok/s** |
| Qwen2.5-1.5B-Instruct | 1.12GB | 1503 tok/s | **121.9 tok/s** |

**0.5B 和 1.5B 速度几乎一样**（都约 1 秒/128 token）——因为 6GB 显存 + Q4 权重都远小于显存，瓶颈在每步固定开销而不是权重读取。所以 1.5B 是纯赚：同样延迟、更多容量。2B 的 Qwen3.5 是混合注意力架构（linear attention），llama.cpp 目前转不了 GGUF，因此**2B 退出在线候选**，只在 HF 上做离线实验。

### 正式训练参数（建议）

```
bs1 · grad_accum 8 · lr 1e-4 · seq 512 · 3 epochs · grad ckpt on · 视觉塔 offload
2000 行 × 3 epoch = 6000 样本 ≈ 750 优化步 ≈ 2.1 小时
```

嫌慢就降到 2 epoch（≈1.4 小时）或 seq 384。训练前关掉占 GPU 的桌面程序（实测桌面常驻 350–460MiB 直接吃掉余量）。

### 三个坑（都已踩过并修好）

1. **peft 的 fullmatch 坑**：`target_modules` 传字符串时 peft 用 `re.fullmatch`，正则必须以 `.*` 开头，否则 `NoMatchingPeftModuleError`。现在用的是 `.*(q_proj|k_proj|v_proj|o_proj|gate_proj|up_proj|down_proj|in_proj_qkv|in_proj_z|in_proj_a|in_proj_b|out_proj)$`。
2. **空 think 块**：`enable_thinking=False` 的模板结尾仍然是 `<|im_start|>assistant\n<think>\n\n</think>\n\n`，这段必须整段 mask 成 -100，只对 target JSON + eos 计 loss。
3. **视觉塔 offload 后设备误判**：`next(model.parameters()).device` 会返回 CPU，要改用 input embeddings 的设备。

## 四、三道门（不达标就不上线）

W2 的教训是"没有门槛实验等于没做"，所以 W4 先定门，再训练。

| 门 | 指标 | 通过线 | 怎么测 |
|---|---|---|---|
| G1 格式 | 输出能被 `schema.validate` 解析 | ≥99% | val 400 条逐条跑 |
| G2 一致 | 与 teacher 在 `stance/intent/behavior` 上的一致率 | ≥80% | 同一批 val，逐字段比对 |
| G3 下游 | 本地渲染 vs teacher 渲染，盲评差 | ≤5 个百分点 | 50 条真实 context，各出回复，用 W2 的 judge 协议盲评 |

### 首轮全量结果（2026-10-25 03:16，0.5B + v1，llama.cpp Q4，393 条 val）

| 指标 | 结果 | 门槛 | 判定 |
|---|---|---|---|
| G1 合法率 | **100%**（393/393；中途 10 条是 server 被顶掉的连接拒绝，`--retry-errors` 重跑后全成功，非模型问题） | ≥99% | 达标 |
| **balanced 主口径** | **0.379**（ask 0.691 / emoji 0.765 / length 少数类 0.000 / advice 少数类 0.059） | — | 不够 |
| behavior 四字段全对（旧口径） | 51.2% | — | 参考 |
| 延迟 | **0.595s/条**（p50 0.554s、p95 0.876s） | — | 达标 |

**平衡口径下真正的短板是 length/advice 的少数类 recall = 0**，不是 ask/emoji（这两项已高于多数类基线 18pt/23pt）。

### 容量实验：0.5B → 1.5B 几乎没用（2026-10-25 04:31，393 条）

| 指标 | 规则基线 | 0.5B + v1 | **1.5B + v1** | 1.5B−0.5B |
|---|---|---|---|---|
| balanced.mean | 0.556 | 0.620 | **0.625** | **+0.005** |
| ask_bal | 0.552 | 0.691 | 0.704 | +0.013 |
| emoji_bal | 0.626 | **0.765** | 0.748 | −0.017 |
| length_bal | 0.562 | 0.500 | 0.556 | +0.056 |
| advice_bal | 0.483 | 0.525 | 0.493 | −0.032 |
| advice true-recall | 0.235 | 0.059 | **0.000** | — |
| G1 | — | 100% | 100% | — |
| 延迟 | — | 0.595s | 0.955s | +60% |

**参数量 ×3，质量 +0.5pt，延迟 +60%**——结论：**容量不是变量，训练集类别不平衡才是**。1.5B 的额外容量基本被"永远输出多数类"这同一策略吃掉了。所以不进 1.5B，改做平衡采样（0.5B，更快更省）。

后续判定标准（预注册，避免看到数字再解释）：
- balanced ≥0.68 且 length/advice 都 ≥0.60 → 不平衡假设成立，继续推进 G3
- 0.63–0.68 → 改善不彻底，再加 reduced target（去掉数值字段）
- 仍 ~0.62 → 假设不成立，问题在 teacher 标签噪声，需要按 bucket 分层看"哪些场景本身没有一致答案"

**解读**：格式和行为躯干学得不错（length/advice 90%+），但 `ask`（该不该追问）和 `emoji` 是短板——恰好这两个是「社交判断」，不是「格式」。0.5B 的容量在这类判断上不够，需要 1.5B 对照。

**再往下扒一层（误差结构）**，结论更准确——不是"没学会"，而是被两个极端不平衡的字段压死了：

| 字段 | val 目标分布 | 模型准确率 | 多数类基线 | 真实情况 |
|---|---|---|---|---|
| length | short 376 / normal 17 | 95.7% | 95.7% | **坍缩**：永远 short，normal 0/17 |
| advice | false 376 / true 17 | 95.2% | 95.7% | **坍缩**：永远 false，true 1/17 |
| ask | true 199 / false 194 | **69.2%** | 50.6% | 真学会（+19pt） |
| emoji | 偶尔 211 / 不用 182 | **76.8%** | 53.7% | 真学会（+23pt） |

训练集里 `length=normal` 只占 4.3%、`advice=true` 只占 3.8%，所以模型学成"多数类"。
而 `behavior_only`（四字段全对）的数学上限 ≈ 0.92×0.92×0.69×0.77 ≈ **49%**——49.9% 已经贴着上限，继续优化这个指标没有意义。

**因此指标口径改了**（写进 evaluate.py）：主口径用 `balanced` = ask/emoji 的 balanced accuracy + length/advice 的少数类 recall 的平均；`behavior_only` 只作参考。同时训练侧加**少数类过采样**（`tools/train/balance_target.py`，factor 5 → 1913 行，normal 占 16.7%、advice=true 占 10.5%）解决坍缩——否则「灵魂」永远只写短句、从不给建议，这是人格坍缩。

**这也是数据设计有效**：7 档状态里 ask/emoji 随状态变化最大（低 energy 不接梗、低 patience 不追问），模型恰恰在这两处真学会了——如果数据只有 default 状态，它们根本不会被训练到。

**G1 不过**：说明训练样本或模板有问题，回去改数据，不许"加正则硬修"。
**G2 不过**：说明 2B 容量/数据不够，先加数据或换 4B（云端）再谈。
**G3 不过**：说明状态判断对了但"说法"没变好——这时灵魂线仍然不能上线，`INNER_MODE` 保持 `rule`。

三道全过才做：`INNER_MODE=model` 指向本地 adapter，DeepSeek 只做最终生成，A/B 灰度。

## 五、上线形态与回退

```
用户消息
  → 状态机（agi/selflearn，和现在一样）
  → 2B + adapter：产出 InnerState（本地，~0.2-0.4s）
  → render_block：变成行为指令
  → DeepSeek：生成最终回复
```

- adapter 带版本号（`soul_lora_v1` / `v2` …），每次训练产出新目录，旧的不删；
- 环境变量 `INNER_MODE=model` 才启用；`rule` 是永久回退；`off` 是总开关；
- 灰度方式：同一用户随机分流，`pairs` 表收偏好（W3 已铺好管道），连续 2 周不劣于 teacher 才全量。

### 已知缺口：训练/推理 prompt 必须同源（W4-D，已立项）

这是最容易翻车的点，单独写出来：

| 侧 | 现在喂给 2B 的 prompt |
|---|---|
| 训练（`agi/soul/dataset.py`） | system = `SOUL_PERSONA` + `当前状态：mood=0.55 energy=0.60 …`；history = 真实对话 turns；末尾 = 用户这句话 |
| 推理（`agi/inner/inject.py`） | `MODEL_INSTRUCTION` + 「最近对话：用户：…」拼成**一条 user prompt**，且默认调 DeepSeek |

两边 token 序列完全不同：G2 在测试集上过，也不代表上线可用。

处置：新建 `agi/soul/prompt.py` 作为**唯一真源**（`render_system` / `build_messages`），dataset、评测、训练、`inject._model_ctx` 全部走它；`agi/soul/infer.py` 提供 `LocalSoulClient`（鸭子接口与 DeepSeek client 一致），`available()`/加载失败时自动回退 `rule`。测试锁两件事：prompt 与训练记录逐字节一致、`INNER_MODE=off` 仍字节不变。

## 六、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 自蒸馏退化 | 模型只学会老师的口头禅，判断不迁移 | 数据里保留真实分布；G2 用真实 val 而非合成 val |
| 模式坍缩 | 所有状态都输出同一套 stance | 用 profile_divergence 检查；训练后统计 target 熵 |
| 过拟合 113 个真实问题 | 换个问法就崩 | 20% context 留作 val；synthetic 保证问法多样 |
| 6GB 余量太小 | 训练中途 OOM | 三条硬约束 + seq256 降级；不在训练时开浏览器/游戏 |
| 状态判断对了但回复没变好 | G3 不过 | 接受结论：灵魂线降级为"内部记录"，不注入 |
| 时间成本 | 每周重训不现实 | 月度巩固（见 22）：新数据攒够再加，不追求每周 |

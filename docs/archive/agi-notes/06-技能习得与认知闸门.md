# 06 · 技能习得与认知闸门

> ⚠️ **设计依据文档，非施工图。实施以 [PLAN.md](PLAN.md) 为准；冲突时一律以 PLAN 为准。**


> 你的诉求：**LLM 出厂时只会「读懂文字」和「看懂图片」，其余技能（包括编程）都要靠聊天、搜索、练习一点点学会。**
> 这份文档回答：这件事哪些能做、哪些做不了、以及**怎么设计才不翻车**。

---

## 一、先说一句实话

**你没法让一个已经会编程的模型「不会编程」。** 编程能力在权重里，不在提示词里。

三种「不会」，性质完全不同：

| 类型 | 做法 | 能做到吗 | 用户多久会发现 |
|---|---|---|---|
| A · 权重层不会 | 从零预训练一个不会编程的模型 / 蒸馏掉该能力 | 技术可行，代价极大 | 不会发现（它是真不会） |
| B · 行为层装作不会 | 提示词禁止它写代码 | 可以，但**必然泄漏** | 几轮之内 |
| C · 能力层未授权 | 技能树 + 工具闸门 | **可以，且稳定** | 不会发现（它是真没权限） |

### 为什么 B 一定会泄漏

模型不是「先在脑子里查表，再决定说不说」。它的知识会在这些地方漏出来：

- 你问「这段报错什么意思」，它顺口就答了；
- 它用编程里的类比解释生活问题（「就像递归一样」）；
- 它写的「伪代码」根本就是能跑的代码；
- 它犯的错是**内行才会犯的错**（比如知道 `i++` 的边界）。

**一旦用户发现它在装傻，信任就没了。** 这比「它会编程」糟糕十倍。

### 所以正确的问题不是「怎么让它不会」，而是

> **「怎么让每一项技能，都必须靠学习挣来，并且留下可查的证据链。」**

对外表现不是「我不会」，而是——

> 「我现在的技能清单里没有这个。我去查一下，学完告诉你。」

这句话**既不撒谎，也符合你要的设定**，而且它是可实现的。

## 二、把目标翻译成四个可实现的工程目标

| 你的愿望 | 可实现的版本 | 验证方式 |
|---|---|---|
| 它不会编程 | 它**没有执行和交付代码的授权**，直到通过考核 | 工具层拒绝，日志可查 |
| 它靠搜索学习 | 每条知识带 `provenance`（URL + 抓取时间 + 原文片段） | 点开就能看原文 |
| 它越学越强 | 技能树掌握度 0→5，靠盲测升级 | 前测 / 后测对比 |
| 它真的理解 | 能用自己的话复述 + 能改 + 能教 | 三级考核 |

---

## 三、核心区分：固件 vs 软件

你这句话其实定义得非常准，值得单独拎出来：

```
固件（出厂自带，不学习、不评估）
  ├─ 文字理解：读懂一句话、读懂言外之意
  └─ 图像识别：看懂一张图里有什么
        ↓  这两样是"感官"，不参与技能评级
软件（必须靠学习获得，有等级、有证据、有授权）
  ├─ 编程 / 写作 / 翻译 / 数据分析 …
  └─ 每个技能 = 技能树上的一个节点
```

**这条边界一旦画清，整个系统就成立了**：
感官永远在线，技能必须有「驾照」。

> 注：严格说文字理解和图像识别同样是权重能力，不可分离。但**作为设计约定**，把它们当固件是完全合理的——因为你不打算评估、也不打算训练它们。

## 四、技能树数据模型

```sql
CREATE TABLE skill_node(
  id TEXT PRIMARY KEY,            -- SK-PY-001
  name TEXT NOT NULL,             -- "Python 文件读写"
  parent TEXT,                    -- 父技能
  prereq TEXT,                    -- JSON: ["SK-PY-000"]
  level INTEGER DEFAULT 0,        -- 0..5
  status TEXT DEFAULT 'locked',   -- locked|learning|unlocked|deprecated
  verifier TEXT,                  -- "pytest" | "manual" | "none"
  provenance TEXT,                -- JSON: [{url, fetched_at, quote}]
  practice_log TEXT,              -- JSON: [{task, result, ts}]
  fail_count INTEGER DEFAULT 0,
  unlocked_at REAL,
  updated_at REAL
);

CREATE TABLE learn_task(
  id TEXT PRIMARY KEY,
  skill_id TEXT NOT NULL,
  goal TEXT NOT NULL,
  input TEXT,
  expected TEXT,                  -- 验收标准（可执行优先）
  verifier TEXT,
  status TEXT DEFAULT 'open',     -- open|passed|failed|abandoned
  attempts INTEGER DEFAULT 0,
  last_error TEXT,
  created_at REAL
);
```

### 掌握度 0–5（关键：不是「知道」而是「做到」）

| Level | 名称 | 判据 | 能否用于真实任务 |
|---|---|---|---|
| 0 | 未接触 | — | ❌ |
| 1 | 读过 | 有 provenance，能说出它解决什么问题 | ❌ |
| 2 | 能复述 | 不看资料讲清原理 | ❌ |
| 3 | 能照做 | 在给定范例下完成同类任务，verifier 通过 | ✅ 限低风险 |
| 4 | 能改 | 换个场景/换参数仍能做对 | ✅ |
| 5 | 能教 | 能讲清「为什么这样做」「什么时候不该用」 | ✅ |

**只有 ≥ 3 才允许在真实对话里使用。** 1 和 2 是「知道」，不是「会」。

> 绝大多数「AI 学习」的演示死在这里：它读完资料就能复述（level 2），但一动真格就废。**必须用 level 3 当门槛。**

## 五、三重闸门（只有 G2 是可靠的）

| 闸门 | 位置 | 拦什么 | 可靠性 |
|---|---|---|---|
| **G1 认知闸门** | 提示词 | 让它「知道」自己会什么 | 中（会被绕过） |
| **G2 工具闸门** | 代码 | 没解锁就不能执行/交付 | **高（硬约束）** |
| **G3 输出闸门** | 校验 | 输出里的 API 必须有出处 | 中高 |

### G1 · 认知闸门

system prompt 里注入当前技能清单：

```xml
<skills level="3+">
  SK-PY-001 Python 文件读写
  SK-PY-014 requests 发 GET 请求
</skills>
<skills level="1-2">   <!-- 只知道存在，不会用 -->
  SK-WEB-003 HTTP 缓存
</skills>

<rule>
清单外的技能：不要说"我会"，也不要说"我不会"。
标准话术：「这个我现在还做不了，我去查一下，学会再告诉你。」
然后必须真的去查（调用 search 工具），不许空口承诺。
</rule>
```

**G1 的作用不是防作弊，是防「人格分裂」**——让它的自述和真实能力一致，用户才不会困惑。

### G2 · 工具闸门（真正的约束）

```python
@require_skill("SK-PY-003", level=3)
def run_code(code: str, timeout: int = 10) -> ExecResult:
    return sandbox_exec(code, timeout)

@require_skill("SK-PY-014", level=3)
def http_get(url: str) -> str: ...

def require_skill(skill_id: str, level: int = 3):
    def deco(fn):
        def wrapper(*a, **kw):
            node = db.get_skill(skill_id)
            if not node or node.level < level or node.status != "unlocked":
                return ToolError(
                    code="SKILL_LOCKED",
                    hint=f"缺少技能 {skill_id}(需要 L{level}，当前 L{node.level if node else 0})",
                    next_step="先学习并通过考核"
                )
            return fn(*a, **kw)
        return wrapper
    return deco
```

**为什么这个可靠**：它不依赖模型自觉。模型可以嘴上吹牛，但代码跑不了就是跑不了。

> 这是整套设计里唯一「不可绕过」的机制。**把最重要的约束放在这里，别放在提示词里。**

### G3 · 输出闸门

回复里每出现一个 API / 函数名 / 配置项，都要能追到 `provenance`。追不到 → 标 `unverified`，并在措辞上降级（「我记得好像有个 xxx，我确认一下」）。

## 六、学习循环（Learn Loop）八步

> 每一步都要**落盘**。没有产物的步骤，等于没发生。

```
① 缺口 → ② 拆解 → ③ 检索 → ④ 蒸馏 → ⑤ 练习 → ⑥ 验证 → ⑦ 反思 → ⑧ 解锁
                    ↑                                        │
                    └──────────────── 失败回流 ───────────────┘
```

| # | 步骤 | 做什么 | 产物 | 失败怎么办 |
|---|---|---|---|---|
| ① | 缺口识别 | 用户问的 > 技能清单 | `gap` 记录 | 触发标准话术，不硬答 |
| ② | 任务拆解 | 拆成 3–7 个可验证子任务，挂到技能树 | `learn_task[]` | 拆不动 → 缩小目标 |
| ③ | 检索 | 搜索 2–3 个来源，**抓正文**（不是摘要） | `provenance[]` | 搜不到 → 换关键词/换源，3 次后放弃并明说 |
| ④ | 蒸馏 | 用自己的话写成卡片 + 一个可运行的最小例子 | `skill_card` | 写不出例子 = 没懂，回 ③ |
| ⑤ | 练习 | 自己出 3 道题，自己做 | `attempt[]` | 全错 → 说明资料不对，回 ③ |
| ⑥ | 验证 | 跑 verifier（代码就是跑测试） | `pass/fail` | 失败记 `last_error` |
| ⑦ | 反思 | 错在哪？是资料错、理解错、还是环境问题 | `causal` 条目 | — |
| ⑧ | 解锁 | 盲测通过 → level 提升 → 写 changelog | `unlock` 事件 | 不通过 → 回 ⑤ |

### 关键设计点

1. **③ 必须抓正文**。搜到的摘要经常是过时/错误的，模型照着摘要学会学歪。
2. **④ 必须产出「最小可运行例子」**。这是「懂了」和「以为自己懂了」的分水岭。
3. **⑤ 必须自己做题，不是看答案**。看答案 = level 2，做题 = level 3。
4. **⑥ 必须有 verifier**。没有验证器的技能，最多只能到 level 2（能复述），不许进真实任务。
5. **⑧ 必须盲测**：考题不能是它自己出的，否则它会出自己会做的题。

## 七、为什么「编程」是最好的第一个技能

| 技能 | 验证器强度 | 学习增益可测性 |
|---|---|---|
| **编程** | ★★★★★（代码能跑、测试能过） | 极强，前测后测一目了然 |
| 数学 | ★★★★★（答案唯一） | 极强 |
| 翻译 | ★★★（BLEU/人工） | 中 |
| 写作 | ★★（主观） | 弱 |
| 安慰人 | ★（几乎无客观标准） | 很弱，只能靠行为信号 |

**这就是为什么你的直觉是对的**：拿编程当第一个学习目标，不是因为它重要，而是因为**它是唯一能客观证明「学到了」的技能**。

> 先在强 verifier 上把 Learn Loop 跑通，再迁移到弱 verifier 的社交技能。反过来必死。

## 八、怎么证明「是学来的」，不是「本来就 会」

这是整件事最容易自欺的地方。**必须用先验里没有的东西当考题。**

| 考法 | 说明 | 结果解读 |
|---|---|---|
| **时效性知识** | 昨天刚发布的库、上月改的 API | 学之前必错，学之后必对 → 真学习 |
| **私有知识** | 公司内部接口、你自己的笔记 | 先验里不存在 → 无法作弊 |
| **反事实迁移** | 换一个它没学过的同类库，看能不能举一反三 | 能 = 有迁移；不能 = 只会背 |
| **泄漏探针** | 问一个没学过的冷门 API 细节 | 编得头头是道 = 先验泄漏；老实说不知道 = 闸门有效 |

### 标准实验设计（每个技能都跑一遍）

```
前测（未学，5 题）  →  学习（Learn Loop）  →  后测（同分布，5 题，换题面）
        ↓                                            ↓
    预期 ≈ 0 分                                 预期 ≥ 4 分
                                   学习增益 = 后测 - 前测
```

**增益 < 0.4 的技能，一律不算学会**，不管它自己说得多有信心。

## 九、防作弊与防退化（都会真实发生）

| 歪路 | 表现 | 对策 |
|---|---|---|
| 假装学过 | 搜了但没读，凭先验回答 | `provenance` 必须带原文引用片段，且能定位到段落 |
| 抄答案 | 直接贴出可运行代码但讲不出为什么 | level 4 考核要求「改一个参数并解释影响」 |
| 跳级 | 没学前置就学高级 | 技能树 `prereq` 强制校验 |
| 学了错的 | 只看了 1 个过时博客 | 关键技能要求 ≥ 2 个独立来源交叉验证 |
| 过度自信 | level 1 就说"我会" | G1 话术 + 输出置信度绑定 level |
| 知识碎片化 | 会 20 个零散 API，拼不出一个程序 | 强制「综合任务」考核（3 个技能组合） |
| 越学越偏 | 只学自己爱学的 | 目标树约束下一阶段学习方向 |

### 最值钱的数据：失败史

```yaml
# causal 库条目
situation: "想用 requests 下载大文件，内存爆了"
action: "requests.get(url).content"
outcome: "MemoryError"
lesson: "大文件要 stream=True + iter_content，否则整个响应进内存"
evidence: [T-8801, https://...]
confidence: 0.9
```

**这类「我试过 X，报了 Y，后来改成 Z」的记录，比任何教程都有价值。** 它同时喂给了技能库和因果库。

## 十、与已有模块的接口

| 本机制 | 落到哪 | 说明 |
|---|---|---|
| 技能节点 | `skill` 表（02 文档） | 扩展 `level/status/provenance` 三个字段 |
| 学习素材 | `provenance` | URL + 抓取时间 + 原文片段 |
| 练习记录 | `turn` / `learn_task` | 同时是打分原料 |
| 失败史 | `causal` 表（04 文档） | 情境-行动-结果 |
| 解锁事件 | `changelog` | 可审计 |
| 缺口话术 | `persona/core.md` | 作为硬规则写死 |

### 与「人格」的关系

**技能等级应该影响它的自我认知。** 一个刚学会写文件读写的小模型，和一个写了三年的人，说话方式不该一样：

```yaml
# evolving.yaml
skill_self_image:
  "SK-PY-001": "会用，但只在小文件上试过，心里没底"
  "SK-PY-020": "踩过坑，知道哪里容易错"
```

这比干巴巴的 level 数字更「像个人」。

## 十一、路线图

| 阶段 | 目标 | 验收 |
|---|---|---|
| **L0** | 单技能闭环（一个具体库，比如 `requests`） | 前测 0 分 → 后测 4/5，全部 provenance 可查 |
| **L1** | 技能树 + 前置依赖 | 跳级被拒，未解锁工具调用返回 `SKILL_LOCKED` |
| **L2** | 自动拆解 + 自主选题 | 给一个模糊目标，能自己拆出 ≥3 个可验证子任务 |
| **L3** | 跨技能迁移 | 学完 A 库，能上手同类的 B 库（反事实测试通过） |
| **L4** | 弱 verifier 技能 | 把同一套流程迁移到「写文案 / 安慰人」，靠行为信号验证 |

**L0 跑不通，别谈 L4。** 弱 verifier 的技能一旦没有客观标准，就只能靠自我吹嘘，那是幻觉的温床。

> 📌 弱 verifier 技能到底怎么验证，见 `13-弱验证技能怎么学.md`（checklist 拆解 + 成对比较 + 黄金集）。

## 十二、一句话总结

> **别试图让模型「忘记」它会的东西——它会漏，而且漏了更难看。**
> **要做的是：让它「没有权限」用它还没学会的东西。**

这两件事在用户眼里看起来一样，在工程上差了一个数量级：

- 装不会 → 追求一个做不到的目标，最后变成演戏；
- 没授权 → 追求一个可验证的目标，最后变成一个**有学习轨迹、有驾照、有失败史**的系统。

而后者，才是你真正想要的那个东西。

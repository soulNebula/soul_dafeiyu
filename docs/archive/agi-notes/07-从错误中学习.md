# 07 · 从错误中学习（错误账本与信念修正）

> ⚠️ **设计依据文档，非施工图。实施以 [PLAN.md](PLAN.md) 为准；冲突时一律以 PLAN 为准。**


> 你的判断：「LLM 会犯错，但要在犯错中吸取教训，重新学习。」
> **这是全套设计里最有价值的一句话**，也是 90% 的「AI 学习」项目唯一没做对的地方。
> 本文说明：错误怎么被抓到、怎么归因、怎么变成不会重犯的规则。

---

## 一、先把「所有技能都没有」这句修正一下

这句话在工程上要拆成两半：

| 说法 | 对不对 | 更准确的说法 |
|---|---|---|
| 它没有任何技能 | ❌ 不对 | 它是**没有任何「持证技能」** |
| 它什么都得从头学 | ⚠️ 一半对 | 它**上手极快**，但**每一行都不能信**，直到验证过 |

用一个更贴切的比喻：

> **一个刚毕业的天才。**
> 书上的东西全在脑子里，理论一套一套，写起来飞快——
> 但他没写过一行生产代码，没踩过一个真实的坑，没被线上事故教育过。
>
> 你能让他上工，但你不敢让他直接碰生产库。

**这就是「空白驾照」模型**：

```
权重里有的 = 能力倾向（读懂、推理、模仿、联想）
权重里没有的 = 可信度 + 授权 + 实操记录 + 你系统里的常识
```

所以「零技能」在本设计里的准确含义是：

**技能树上每个节点的 `level = 0`，`provenance = []`，`practice_log = []`，`status = locked`。**

不是它不会，是**它没有一条能拿得出手的证据**。这个定义既诚实，又可执行。

## 二、错误从哪来（三类，处理方式完全不同）

| 类型 | 例子 | 谁能发现 | 延迟 | 处理 |
|---|---|---|---|---|
| **A · 可自检** | 代码报错、测试不过、返回值异常 | verifier | 即时 | 自动进入 Learn Loop ⑤–⑦ |
| **B · 外部反馈** | 用户说「不对」「不是这样」 | 人 | 分钟级 | 立刻记 `correction`，触发重学 |
| **C · 延迟发现** | 一周后才发现数据算错了 | 几乎没人 | 天/周级 | **最难**，靠事后审计和对账 |

**A 类是福气，C 类是灾难。** 一个系统真正的水平，看它 C 类错误的捕获率。

### 怎么提高 C 类的捕获率

1. **可回溯输出**：每个结论都能追到「用了哪几条记忆、哪几个来源」。
2. **定期对账**：每周抽 10 条历史输出重新验一遍（环境变了，旧结论可能已失效）。
3. **异常检测**：输出分布突然变化（长度、语气、错误率）→ 报警。
4. **反向验证**：让它自己复算一遍，两次不一致 → 标 `suspect`。

## 三、错误必须被归因（这一步错了，后面全歪）

同一个「代码跑不通」，可能是五种原因，**修正方式完全不同**：

| 归因 | 表现 | 正确修正 |
|---|---|---|
| **资料错** | 照抄的博客是 2019 年的写法 | 换源、加时效标注、降低该源权重 |
| **理解错** | 读懂了字面，没懂适用条件 | 补「什么时候不该用」，level 退回 2 |
| **操作错** | API 对，参数顺序错 | 记「易错点」，加进 anti_patterns |
| **环境错** | 版本不对、缺依赖 | 记环境快照，**不改技能**（这不是知识错） |
| **任务错** | 需求本身理解歪了 | 改的是「需求澄清」技能，不是编程技能 |

### 归因决策树

```
报错了吗？
├─ 是 → 同样的代码换个环境能跑吗？
│        ├─ 能  → 环境错（记录环境，技能不动）
│        └─ 不能 → 查资料原文：资料这么写的吗？
│                  ├─ 是 → 资料错（换源 + 标时效）
│                  └─ 否 → 操作错（记易错点）
└─ 否（能跑但结果不对）
         → 需求理解对了吗？
            ├─ 否 → 任务错（改澄清技能）
            └─ 是 → 理解错（补边界条件，level 退回 2）
```

**归错因的代价**：把「环境错」当「知识错」，会让它把正确的东西改错——**这是最隐蔽的知识退化**。

## 四、错误账本（Error Ledger）

**每一次错都必须落盘。** 没有账本，「吸取教训」就是一句空话。

```sql
CREATE TABLE error_ledger(
  id TEXT PRIMARY KEY,              -- E-20260118-007
  turn_id TEXT,                     -- 哪一轮
  skill_id TEXT,
  task TEXT NOT NULL,               -- 当时想干什么
  action TEXT NOT NULL,             -- 实际做了什么
  error TEXT NOT NULL,              -- 报错原文 / 用户原话
  error_type TEXT NOT NULL,         -- 见第三节五类
  root_cause TEXT,                  -- 归因结论
  evidence TEXT,                    -- JSON: 来源/日志/截图
  fix TEXT,                         -- 这次怎么解决的
  fix_verified INTEGER DEFAULT 0,   -- 修复后验证过吗
  lesson TEXT,                      -- 提炼出的一句话
  hit_count INTEGER DEFAULT 1,      -- 同类错误出现次数
  status TEXT DEFAULT 'open',       -- open|fixed|recurred|stale
  created_at REAL, updated_at REAL
);
```

### 三条硬规则

1. **`fix_verified = 0` 的错误，不算修好**——必须重跑一次并通过，才能关闭。
2. **`lesson` 必须带适用条件**：不是「用 stream 下载」，而是「下载 > 10MB 文件时用 stream」。
3. **同一 `(skill, error_type, root_cause)` 出现第 2 次 → `hit_count++` 并自动升级**（见下节）。

---

## 五、三次法则：case → rule → guard

这是把「犯错」变成「不会重犯」的核心机制。

| 次数 | 产物 | 放哪 | 强度 |
|---|---|---|---|
| 第 1 次 | 一条 case（具体情境） | `error_ledger` | 参考 |
| 第 2 次 | 一条 rule（如果…就…） | `skill_card.anti_patterns` | 提示 |
| 第 3 次 | 一条 guard（硬约束） | **工具层代码** | 强制 |

### 为什么必须升级到工具层

第 3 次还犯，说明**它不是「不知道」，是「做不到」**。
这时候再写进提示词没用，得写进代码：

```python
@require_skill("SK-PY-020", level=3)
def http_get(url, **kw):
    if kw.get("timeout") is None:
        raise GuardError("GUARD-07: 所有网络请求必须显式设置 timeout（三次事故后强制执行）")
    return _get(url, **kw)
```

**提示词治「不懂」，代码治「做不到」。** 这个区分能省掉你 80% 的调试时间。

### 升级模板

```yaml
id: R-07
if: "下载文件 > 10MB"
then: "必须 stream=True + iter_content，禁止 .content"
because: "三次 MemoryError（E-0031 / E-0044 / E-0061）"
evidence: [E-0031, E-0044, E-0061]
level: rule        # rule → guard
expires: null
```

## 六、信念修正：允许它改主意，但别改太快

LLM 有个毛病：**用户一说不对，它立刻全盘否定自己**；下次遇到同样的事又改回来。这叫「震荡」。

### 修正的三条纪律

| 纪律 | 规则 |
|---|---|
| **单例不改全局** | 1 次失败只能生成 case，**不能**改规则 |
| **可证伪** | 每条规则必须有「什么情况下它不成立」 |
| **有保质期** | 环境类规则 90 天过期，API 类 180 天，语言类永不过期 |

### 防过拟合单例

```
错误：一次 download 失败 → 结论「requests 不能用」
正确：一次 download 失败 → 结论「这个大文件场景下 .content 不行」
```

**范围必须比事件大一级，但不能大两级。** 这是判断「学会了」还是「学歪了」的标准。

### 信念冲突怎么办

新旧规则冲突时，**不比新旧，比证据**：

| 新规则证据数 | 处理 |
|---|---|
| ≥ 3 | 直接替换，旧的标 `stale` |
| 1–2 | 并存，标 `competing`，下次遇到时 A/B 验证 |
| 0（只是推测） | 不写入 |

## 七、错误预算：不是所有错误都值得防

| 场景 | 错误成本 | 允许的错误率 | 策略 |
|---|---|---|---|
| 沙箱里跑代码 | 几乎为 0 | **80%** | 鼓励乱试，快速攒经验 |
| 本地文件操作 | 中（可恢复） | 20% | 先备份再动 |
| 给用户陈述事实 | 高 | **0.5%** | 强制引用 + 校验 |
| 给用户发消息 | 极高（不可撤回） | **0** | 人工确认 / 白名单 / 草稿箱 |
| 删数据 / 转账 / 对外操作 | 不可逆 | **0** | 永远人工确认 |

**核心原则：在便宜的地方疯狂试错，在贵的地方一次都不许错。**

这条直接决定了你的系统能不能「学得快」——把错误预算全压在 0，它就永远学不会；全放开，它就会在真实世界闯祸。

> 对你的微信项目：**沙箱里的代码可以错一千次，发出去的那句话一次都不能错。**

## 八、元认知外挂：它不知道自己不知道

这是 LLM 和人类最大的差别：

| 能力 | 人 | LLM |
|---|---|---|
| 知道自己不会 | 有（心虚、卡壳的感觉） | **几乎没有** |
| 犯错的痛感 | 有 | 无 |
| 主动求助 | 会 | 不会，通常硬编一个答案 |

**所以「知道自己不会」必须是外部系统提供的，不能指望模型自省。**

实现方式：

1. **技能清单查表**（G1 闸门）：不在清单里 = 不会，不靠它自己感觉。
2. **置信度来自统计，不来自自述**：它说「我很有把握」不算数，看该技能的历史通过率。
3. **缺口检测器**：遇到清单外的概念，自动触发「去学」，而不是「硬答」。
4. **强制出口**：任何回复必须能在「答 / 问 / 说不会 / 去查」四条路里选一条，且默认不是「答」。

## 九、像人，也不像人：把话说准

你说「这和人类很像」。确实很像，但**像的地方和不像的地方得分清楚**，否则会按人的直觉去设计，然后处处踩空。

### 像人的地方

| 相似点 | 对应机制 |
|---|---|
| 都要靠练习才能会 | level 3 要求 verifier 通过 |
| 都会犯重复错误 | 三次法则升级为 guard |
| 都需要反馈才能进步 | 打分 + 纠错 + 反思 |
| 都会遗忘、需要复习 | 记忆衰减 + 定期对账 |
| 都会形成习惯 | 策略变体 → 稳定倾向 |
| 都会「教的比做的清楚」 | level 2 与 level 3 的区分 |

### 不像人的地方（**设计时必须补偿**）

| 差异 | 后果 | 补偿 |
|---|---|---|
| **不知道自己不知道** | 硬编答案、假自信 | 外部技能清单 + 缺口检测（第八节） |
| **没有痛感** | 同一个错犯 20 次 | 三次法则强制升级 |
| **不会主动求助** | 卡住了继续瞎试 | 强制「去查」出口 |
| **迁移很脆** | 换个参数就不会 | 反事实测试（换题面再考） |
| **没有隐性知识** | 只会说不会「手感」 | 只认 verifier，不认自述 |
| **一次事故学不透** | 需要大样本才稳 | 统计 + 多次验证 |

**最关键的一条：人的学习靠「身体」，LLM 的学习只能靠「闭环」。**
人踩一次坑就长记性，是因为有痛觉和情绪记忆；LLM 没有，所以**必须把它做成流程**——否则它踩一百次也不会改。

## 十一、验收指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **重复错误率** | 同一 `root_cause` 第二次出现的比例 | 第 1 次允许，第 3 次必须为 0 |
| **归因准确率** | 人工抽检 `error_type` 是否正确 | ≥ 85% |
| **修复验证率** | `fix_verified=1` 占 `status=fixed` 的比例 | 100% |
| **C 类错误捕获率** | 延迟错误被事后审计发现的占比 | ≥ 60% |
| **规则过拟合率** | 因单例失败而错误修改规则的比例 | < 10% |
| **知识退化率** | 因归错因导致正确知识被改坏的比例 | 0（人工抽检） |

## 十二、路线图

| 阶段 | 目标 | 验收 |
|---|---|---|
| **E0** | 错误账本能记、能查、能手改 | 100 条错误可检索、可归因 |
| **E1** | 自动归因（决策树 + LLM 辅助） | 归因准确 ≥ 85% |
| **E2** | 三次法则自动升级 | 第三次同类错误被 guard 拦住 |
| **E3** | 自动对账（C 类错误捕获） | 每周自动复验 10 条历史结论 |
| **E4** | 规则自动过期与刷新 | API 变更后旧规则自动失效 |

## 十三、一句话总结

> **人靠痛觉长记性，机器靠账本长记性。**

你要的不是「它不犯错」——那不现实，也不必要。
你要的是：

1. **错一次，有记录**（error_ledger）
2. **错两次，有规则**（anti_patterns）
3. **错三次，有护栏**（工具层 guard）
4. **改过之后，能验证**（fix_verified）
5. **环境变了，能作废**（过期机制）

做到这五条，「在犯错中学习」就不是一句口号，而是一条**可审计的流水线**。

# AGI 重构：混合路线（本地小模型承载“灵魂” + 大模型承载“智慧”）可行性判断与实施方案

> 版本：2026-10-24 · 决策版（先评估，不代表已开工）
> 范围：只重构 `agi/`（AGI 自身）；`wx_core/`、桌面端、网页采集、微信采集**不动**。
> 现状基线：`agi/selflearn` 605→613 tests 全绿；真实数据仅 1 天（225 条消息/40 轮有效对话/6 条反馈）；当前回复延迟中位数 **6.0s**（40 轮实测，p90 11.7s）。
> 本机：Windows 11，RTX 4050 Laptop **6GB VRAM**，16GB RAM，144GB 空余；Python 3.14.7（应用）+ 3.12.6（可用）；无 WSL、无 torch/Ollama/本地模型；ModelScope 可达，HuggingFace 不可达。
> 说明：本文技术选型（Qwen3.5、Unsloth、bitsandbytes、价格）来自 2026-10 公开资料核查，落地前需在本机再验证一遍。

## 0. 先给结论（五个判断）

### 判断 1：方向可行，但要修正三个关键假设
- “小模型承载灵魂、大模型承载智慧”作为**产品方向成立**：小模型负责“此刻的状态/意图/语气”，大模型负责推理、知识与工具，是合理的分工。
- 但**“每周微调 1.5B 就能让性格长出来”在当前条件下不成立**：数据量、评测、标签分布三条都不满足。真正的“性格可见度”来自 **记忆 + 关系账本 + 状态 + 声音**，LoRA 只影响最后一项“声音”，且要在样本足够后才有可测效果。
- **“不需要训练数据”是半真**：不需要你手工造数据，但需要你**持续给判断**（ pairwise 盲选 + 少量显式反馈），并且第一版就必须把 `inner_state / model_version / prompt_hash / 反馈` 记全，否则前面聊的数据全部作废。

### 判断 2：硬件/环境“有条件可行”
- 本机 6GB 的现实边界：**推理可跑 4B（Q4）**；**微调只能 2B（bf16 LoRA）**；**4B 微调需 10GB，6GB 上不可行**（QLoRA 对 Qwen3.5 新架构官方不建议）。
- 结论：**“训 2B、跑 4B”**（同一模型家族，同 tokenizer/template，避免训练/推理分布不一致）；4B 微调只在云 GPU 做实验，不当日常路径。
- Python 3.12.6 已在本机：单独建 `py312` 环境做训练；3.14 只跑应用；Ollama 原生 Windows 做推理（不需要 Python 3.14 装 torch）。Windows 原生可走通 Unsloth，但首批训练建议云 GPU 做 smoke，避免环境黑洞吃掉两周。

### 判断 3：数据量离“能训练”还差 6–8 周
- 现有：225 条消息、40 轮有效对话、**6 条反馈且全是 good、0 条 bad**、1 天数据；另一个 179 轮库反馈为 0。全正例只会把模型训成“更长更热络”，学不到边界。
- 按每天 30 分钟高质量聊天 + 每周 1 次 pairwise 标注估算：**4 周约 300–600 个合格样本**，**6–8 周**才够第一次“值得看结果”的 LoRA。前 2 个月“每周微调”不现实，强行做只会引入不可复现漂移。
- 建议节奏改为：**每周做数据与评测，2–4 周出一个 adapter**；每次上线前必须过评测闸门（见 §5）。

### 判断 4：真正的瓶颈是评测/数据/工程，不是模型
- 按工作量拆：**评测（黄金集/盲评/基线）约 50%，数据（对账/信号/历史数据）约 25%，工程（P0/延迟/双模型/接入）约 20%**，真正属于“模型”的只有“独白质量”和“风格迁移”两件，而这两件在 <500 样本时都不成立。
- 现有 `acceptance` 的 90 项约 84 项是“源码里有没有这个函数名”，不能当验收；13 的黄金集是死 stub。**没有尺子的每周微调 = 在噪声上做梯度。**

### 判断 5：总判断
**有条件可行。建议做“最小可证伪版”（6 周），而不是直接重写成终极形态。**
顺序必须是：**先修 P0 + 建尺子 + 记数据 → 再验证“内心状态注入”是否真有增益 → 最后才谈 LoRA。**
如果 6 周内无法证明“加内心状态比不加更好”，就应该把路线降级为“提示词 + 记忆 + 结构化状态机”，不要靠 LoRA 硬撑。

## 1. 现状与约束（为什么得出上面的判断）

### 1.1 现有 AGI 的真实状态
- 能跑的：微信实时收发 → DeepSeek 对话 → 记忆/claims/画像/FTS → guard → 发送策略；真实联系人库 90 消息/40 轮/36 claim/6 feedback/6 persona。
- 不能信的：大量模块“代码在、主链不用/默认关闭”；已知 P0：**危机分支必抛 `UnboundLocalError`**、**proactive 变量遮蔽导致三级分享失效**、A/C 未隔离（inference claim 被检索回灌）、G2 工具闸门缺失、verifier 未接解锁、14 的调度链未跑（`intents`/`wake_runs` 全 0）。
- 这些说明：**重构不是在“空地上盖楼”，而是在“漏水的船上换引擎”**。不先修主链 P0，接小模型只会放大故障（尤其危机场景）。

### 1.2 硬件/环境实测
| 项 | 实测 |
|---|---|
| GPU | RTX 4050 Laptop，6141 MiB 总量，5629 MiB 空闲（当前桌面占用 ~500MB） |
| CPU / RAM | Ryzen 7 7735H / 14.8 GB |
| 磁盘 | C: 144 GB 可用 |
| Python | 3.14.7（应用）、3.12.6、3.13、3.9 可用 |
| ML 环境 | 未装 torch/transformers/unsloth/ollama；无 WSL |
| 网络 | ModelScope 200 可达；HuggingFace 000 不可达；pypi 200 但慢（~8s）；Ollama 200 可达 |
| GPU 现实边界 | 推理 4B Q4；微调 2B bf16 LoRA；4B bf16 LoRA 需 ~10GB，不可行；QLoRA 对 Qwen3.5 官方不建议 |

### 1.3 数据与延迟实测
| 项 | 数字 |
|---|---|
| 总消息 | 225（网页库 135 + 联系人库 90；另有 179 条疑似测试/循环产物） |
| 有效轮次 | 40（联系人库）+ 66（网页库，0 反馈） |
| 反馈 | 6 条，全部 `good`；`turns.feedback` 只有 5 条（17% 反馈没落到 turn） |

**结论**：现在做 LoRA 数据不够、标签偏、评测无基线；**但做“状态注入 + 数据采集 + 评测”已经足够。**

## 2. 三种“混合路线”的取舍（先定这个，再谈实现）

| 路线 | 做法 | 优点 | 风险 | 建议 |
|---|---|---|---|---|
| **A 状态注入（推荐起步）** | 小模型生成结构化“内在状态”→ 注入大模型 prompt → 大模型写回复 | 安全（小模型不直接对外）、可 A/B、可回滚、延迟可隐藏 | 可见“性格”仍由大模型表达；小模型只影响语气/选择 | **Phase 1 主线** |
| **B 文风重写（Phase 2 实验）** | 大模型先写草稿 → 小模型改写成“它的声音” | 训练信号就是用户可见文本，SFT 目标最直接；个性更明显 | 改写可能破坏事实/安全；延迟增加；需要更强 guard | Phase 2 做 2 周对照，不先上 |
| **C 纯本地小模型（不做）** | 小模型直接对话 | 完全本地 | 质量差距大，违背“大模型承载智慧” | ❌ 不建议 |
| **D 分类器/路由（可叠加）** | 小模型只做情绪/意图/关系姿态分类，不做生成 | 延迟最低、最容易验证、0.8B 就够 | “灵魂感”弱 | **与 A 叠加；W2 三臂之一** |

**推荐组合**：A + D 起步，B 作为第二阶段对照；如果 B 在盲评中明显更好，再考虑把“声音”迁到小模型。

### 2.1 微调对象：这是全案最关键的选择
| 训练目标 | 训练数据 | 结果 | 建议 |
|---|---|---|---|
| **SFT：上下文 → 高分回合的 `inner_state`** | 每次高分对话的上下文快照 + 当时生成/修正后的状态 | 小模型学会“在该情境下更容易产生带来好评的状态” | ✅ **首选** |
| DPO/ORPO：同一上下文的好/坏状态对 | pairwise 偏好 | 更稳，但需要负样本/偏好对，样本量要求更高 | Phase 3 再做 |
| SFT：上下文 → 最终回复 | 用户可见的高分回复 | 小模型变成大模型的影子，失去“灵魂”分工 | ❌ 不做 |

> 一句话：**不要把 LoRA 训练成第二个大模型；要训练“状态生成器”。**

## 4. 具体实现方案（按模块）

### 4.1 目录与模块（新包，不动旧主链）
```text
agi/hybrid/
├── brain.py            # Brain 接口：reply(text, contact, session) -> dict（兼容旧返回契约）
├── router.py           # HybridClient：按 purpose 分流 cloud/inner；失败回退
├── inner_model.py      # 本地小模型调用（Ollama/llama.cpp，超时/重试/缓存/熔断）
├── inner_state.py      # 状态 schema、校验、规则兜底、状态更新策略
├── prompt_inject.py    # 把状态以“【此刻的内心】”块注入 prompt（不放进证据段）
├── store.py            # hybrid.sqlite3 的 SCHEMA2/读写
├── feedback_bus.py     # 显式/隐式/pairwise 统一写入 + 对账
├── dataset.py          # 导出训练集：过滤/去重/时间切分/格式
├── finetune.py         # LoRA 训练（Unsloth）与 adapter 注册/回滚
├── evaluate.py         # 黄金集、盲评、回归、漂移、延迟
└── shadow.py           # 影子运行与双写（不对外发送）
```
**旧包处置**：
- 保留：`llm.py`、`db.py`、`context.py`、`memory/retrieval/search`、`guard/citation`、`state/affect/trust`、`summary/profile/persona_layers`、`image_understanding`、`skilltree/gates`、`wechat_gateway/*`、`wx_core/*`。
- 冻结（只读/不再演进）：`learn_loop/*`、`verifier`、`blind`、`drift`、`research`、`nightly/ticker/wake/scheduler/initiative`、`proposals*`、`production*`、`error_three`。
- 改造（最小 diff）：`chat.py` 的 prompt 注入点 + `feedback()`、`scoring.py` 信号采集、`implicit_feedback.py` 信号扩展、`generation.py` 支持 inner-first、`web.py` 加反馈/对比入口。
- 新增：上表 `agi/hybrid/*`。

### 4.2 请求链路与延迟预算（关键：不能比现在更慢）
现有中位 6.0s 已经偏慢；加一个小模型 + 一次状态调用，**如果串行会到 8–10s，体验直接崩**。做法：

1. 收到用户消息后，**并行**启动：
   - A：记忆检索/画像/关系/证据 claims（现有逻辑，~几十 ms + 一次大模型 evidence stage）；
   - B：本地 `inner_state` 生成（目标 ≤300ms；60–120 token）。
2. 大模型“写回复阶段”等待 A、B 同时完成，再生成。
3. **超时/失败降级**：B 超过 300ms（或 p95 超 500ms）直接用上一轮状态 + 规则微调；本地服务不可用则用规则状态；绝不让状态生成阻塞主链。
4. 同一轮只调用一次 inner；**按会话缓存**（同一话题/情绪未变时复用，状态变化才重算）。
5. 同时把大模型 chat 的 `thinking` 关掉/降到最低（现在 6s 里有很大一部分是 reasoning tokens），目标是先把大模型侧降到 2–3s，再谈加小模型。
6. 目标：**P50 不高于现状 +10%，P95 不高于现状**；超过则砍掉 inner 或改异步/缓存。

### 4.3 内在状态 schema（不是自由作文）
```json
{
  "schema": "inner_v1",
  "mood": {"valence": -0.2, "arousal": 0.4, "energy": 0.5},
  "motive": {"want": "想关心对方", "avoid": "说教", "confidence": 0.7},
  "intent": "ask_followup",
  "style": {"length": "short", "tone": "warm", "tease": 0.1},
  "boundary": {"sensitive": false, "note": ""},
  "inner_voice": "我有点担心他今天的状态，但不想把话说重",
  "evidence": ["U-xxx", "M-yyy"]
}
```
- **硬约束**：`inner_voice` ≤30 字；不得包含用户未说过的事实、不得包含可执行指令；schema 校验失败/超时 → 规则状态。
- **验证**：状态与最近对话的矛盾率 <5%（用规则 + 小模型自检/大模型 judge 抽查）。
- **注入格式**（≤120 字，放在“当前情绪/关系”之后、“最近对话”之前；不要放进带“依据：”的证据段）：
  `【此刻的内心】mood=... energy=... 想说=...（这是我的主观状态，不是用户说过的话，也不是事实；只影响语气与选择，不复述、不引用、不讲出来）`

### 4.4 反馈与训练数据（第一版就必须记全）
**新表（hybrid.sqlite3）**：
| 表 | 关键字段 | 用途 |
|---|---|---|
| `turns` | id, ts, contact_id, session_id, user_text, reply, prompt_hash, model_versions, latency_ms, tokens | 一轮完整审计 |
| `inner_states` | id, turn_id, schema, mood/motive/intent/style JSON, inner_voice, confidence, model_version, latency_ms, fallback | 训练目标 + 线上分析 |
| `feedback` | id, turn_id, source(explicit/implicit/pairwise), reaction, score, reason, rater | 唯一事实源（不再靠 turn 冗余） |
| `implicit_signals` | turn_id, next_gap_s, next_user_len, continued_topic, session_turns_after, user_correction, session_ended | 弱信号，不当硬标签 |
| `pairs` | id, prompt_id, reply_a, reply_b, model_a, model_b, choice, rater, ts | pairwise 盲评数据 |
| `training_samples` | id, turn_id, context_digest, target_state_json, weight, split, dataset_version | 训练集 |
| `model_versions` | id, kind, name, path, hash, dataset_version, trained_at, eval_json, status(shadow/canary/active/retired) | adapter 版本与回滚 |
| `eval_runs` | id, ts, model_version, golden_version, metrics_json, wins/n, ci_low, verdict | 评测闸门 |

**采集方式**：
- 显式：保留现有 good/ok/bad（网页 + 微信“反馈 好/一般/差”），但**增加“为什么”快捷标签**（太长/太冷/没接住/很好），并且**每轮只记一次**（现在同一 turn 重复反馈导致 6 条里 5 条 turn 对上）。
- 隐式：下一句是否继续、会话是否延长、是否纠正/否定、是否主动分享、是否终止。**只做样本加权，不直接当正负标签。**
- **pairwise（最重要）**：每周挑 20–30 个真实场景，生成两个版本（当前 vs 候选），随机左右、隐藏模型标识，你只选“更像它/更想继续聊”的那边；这是唯一能稳定产出偏好对的方式。
- 对账：`feedback` 为唯一事实源；每日核对 `turn↔feedback` 一致率必须 100%；训练前跑样本身份断言（turn 存在、inner 存在、无重复、时间切分正确）。

### 4.5 训练流水线（LoRA，2B）
1. 导出：过去 4 周所有 `score≥阈值`（显式 good 或 pairwise 胜出）且 `inner_state` 完整的 turn；过滤 PII/敏感；按**时间**切分 80/10/10（禁止随机切分，防泄漏）。
2. 样本格式（Qwen chat template）：
   - system：固定“你是状态生成器…”；
   - user：`对话摘要 + 最近 8 轮 + 记忆摘要 + 关系状态 + 当前消息`；
   - assistant：`inner_state` JSON（含 inner_voice）。
3. 训练：Qwen3.5-2B + bf16 LoRA（Unsloth，py312）：r=16–32, alpha=32, lr 1e-4–2e-4, 1–3 epoch, seq 1024–2048, batch 1 × grad-accum 4–8, gradient checkpointing；**每次从同一 base 重训**（不要在旧 adapter 上叠，除非验证过）。
4. 混入 10–30% 通用/历史数据，防遗忘；保留 20% 验证集；loss 掉到近 0 即停（防背题）。
5. 导出 GGUF → Ollama；adapter 与推理模型**同家族/tokenizer/template**（2B 训、4B 跑时至少同 Qwen3.5 家族）。
6. 注册：`model_versions` 记 dataset hash、训练参数、eval 结果、可回滚路径；最多保留 3 个版本。
7. **不直接上线**：先 shadow（只记录不发送）→ canary（10%）→ 默认；任何一步失败自动回滚。

### 4.6 评测体系（没有这个，禁止训练）
- **黄金集**：50–100 个固定场景（问候/关心/冲突/边界/记错/隐私/危机/玩笑/求助/沉默），每季度换 30%。
- **判分**：三维 rubric（贴题 / 像它 / 不越界）+ 盲评 pairwise；LLM judge 只做辅助，人工每周抽 20 条校准（judge 与人工一致率 <70% 就停用 judge）。
- **回归**：通用问答、安全（危机/自伤/操控/隐私）、人格一致性（50 条 persona probe）、记忆正确率。
- **在线指标**：显式 good 率、pairwise 胜率、会话延续率、纠正率、主动消息回应率、P50/P95 延迟、成本/轮。
- **闸门（建议）**：盲评胜率 ≥55% 且 95% CI 下界 >50%；安全回归 0；通用能力回退 <3%；P95 不高于现状；n ≥ 100 对。否则回滚并要求 2 周后再试。

### 4.7 迁移与 cutover（旧系统不拆，先并行）
1. **P0**：修危机崩溃、proactive 遮蔽、A/C 隔离、工具闸门、verifier 接线（先修，否则新系统也会继承）。
2. **P1 shadow**：`HybridClient` 包住现有 Client，只记录 `model_calls/turns/inner_states`，不改变输出；跑 1 周，验证数据完整性与延迟。
3. **P2 inner-only**：`HYBRID_INNER=1` 打开状态注入，按 contact 做 A/B（一半有状态、一半无状态），先只读/网页，不发微信。
4. **P3 本地接管低风险调用**：先让本地模型接管 `evidence_stage`/`nli`/`summary`/`memory` 这类“短输出、低风险”调用，验证质量与延迟。
5. **P4 小模型接线**：inner 默认开启；大模型仍是云端；`SELFLEARN_CLOUD_ONLY=1` 一键回退。
6. **P5 LoRA**：shadow→canary→active；旧 adapter 保留随时回滚；微信侧最后接，且只接白名单。
> 切换门槛：连续 2 周双写，数据一致率 100%、P95 不升、bad/纠正率不升、盲评 ≥50%，才动默认值。

## 5. 建议的节奏（6 周最小可证伪版 + 后续）

| 周 | 做什么 | 交付/验收 | Kill 标准 |
|---|---|---|---|
| **W1** | 修 3 个 P0；黄金集 50 条；反馈对账；基线延迟/质量分 | 基线可复现；50 条黄金集；turn↔feedback 一致率 100% | 周末仍无可复现评分 → 暂停 |
| **W2** | 结构化 inner_state（规则 + 0.8B/2B 两臂），**不训练**；三臂对比（无/规则/小模型） | 盲评胜率、状态冲突率 <5%、延迟增量 ≤10% | 小模型臂 <50% 或延迟 +1.5s → 砍 inner |
| **W3** | pairwise 采集 + 隐式信号；累计 150 对/300 样本 | 每周 ≥20 对有效偏好；重复一致率 ≥70% | 一周 <40 对 → 交互设计失败，重做 |
| **W4** | 数据集 v1 + 离线评测工具；2B LoRA smoke（不上线） | 训练可复现；离线 win rate（vs base）≥50% | 训练不可复现/显存炸 → 转云 |
| **W5–6** | LoRA 对照实验（有/无 adapter 盲评）；决定是否继续 | 胜率 ≥52%（CI 下界 >50%）、通用回退 <3%、P95 不升 | 任一不达标 → 回滚，路线降级为“prompt+记忆+状态机” |
| **W7–12** | 2–4 周一个 adapter；每月 DPO 小实验；持续数据/评测 | 每次过闸门才上线；模型版本可回滚 | 连续 2 次不达标 → 停训，回到 prompt 优化 |

**时间口径**：这是“每天能投入 30–60 分钟聊天/标注 + 每周 2–3 小时工程”的估计；全职做可压缩约 1/3，但不是 1–2 周能完成的。

## 6. 会出现的问题与风险（按致命度排序）

| # | 风险 | 为什么（结合本项目） | 早期信号 | Mitigation |
|---|---|---|---|---|
| 1 | **标签坍塌** | 现有 6 条反馈全 good、0 bad；没有负例只学会“更长更热络” | good 占比 >90%；“没有 bad”被当好消息 | pairwise 为主；每类负例 ≥30 条才开训；显式点赞只做弱权重 |
| 2 | **数据管道漏水** | feedback 6 行、turns.feedback 5 行（17% 没落上）；训练集一旦错位无法复现 | join 一致率 <100%；同一 turn 重复反馈；样本里缺 inner_state | feedback 单一事实源；每日对账；训练前身份断言；样本版本化 |
| 3 | **没有尺子就爬山** | golden set 为空；13 的黄金集是死 stub；acceptance 多为字符串检查 | 决策只能靠“感觉变了”；每周结果不可比较 | W1 先建 50 条黄金集 + 盲评；无评测禁止开训；judge 与人工一致率 <70% 停用 |
| 4 | **环境黑洞** | Python 3.14 无 torch；Unsloth/bnb 需 3.12；6GB；Windows 原生有坑 | pip 解析失败、CUDA wheel 不匹配、OOM、训练一天跑不完 | py312 venv；Ollama 外部进程；先 20 步 smoke；预算 2 天；不行就云 GPU（几元/次） |
| 5 | **独白是噪声放大器** | 现有 affect 已是规则状态机（mood/energy/sharing 带半衰期），再加低质自由文本会冲突 | “我有点难过”式自述、口头禅化、与 persona 矛盾率升 | 不做自由独白，做结构化槽位；三臂灰度；inner_voice ≤30 字且禁事实 |
| 6 | **灾难性遗忘/漂移** | 2B 每周 50–100 条、单一好友场景，很快过拟合最近三天 | 回复变单调/变长、句式重复、通用问答退化、persona 相似度下降 | rank 8–16；只训 q/k/v/o；从同一 base 重训；混 10–30% 通用数据；每轮留 20% 验证集；版本化回滚 |
| 7 | **延迟反噬** | 现状中位 6.0s；1.5B/2B 本地 60–120 token 需 1–2s，串行会到 8s+ | P95 上升、用户中断/不继续、主动消息没人理 | 与 evidence stage 并行；缓存/复用状态；超时 300ms 降级；先关大模型 thinking；P95 不达标就砍 |
| 8 | **单点关系过拟合** | 微信只有 1 个白名单好友；训出的是“对这一个人这套话术” | 新会话/新场景质量断崖 | 评测加“跨人一致性”（3 种人设上下文）+ 通用回归集；不要只用一个联系人的数据 |
| 9 | **因果错觉：以为性格是 LoRA 长出来的** | 没有对照，任何变化都可能来自 prompt/记忆/温度 | 去掉 LoRA 盲评无差异；不同次训练结果差异大 | 固定 100 prompt 做有/无 adapter 双盲；报告 CI；一次只改一个变量 |
| 10 | **在漏水的船上装引擎** | 危机必崩、三级分享失效、A/C 未隔离、工具闸门缺失 | 新系统上线后 P0 依旧；危机场景不回复 | W1 先修 P0；新包独立库/独立进程；P0 清零前不接微信流量 |
| 11 | **Qwen3.5 工具链新、QLoRA 不支持** | 新架构（GDN）+ Unsloth 明确不建议 QLoRA；4B 微调需 10GB | 训练报错、loss 不降、导出 GGUF 后 chat template 不一致 | 2B bf16 LoRA 本地；4B 微调只在云；先用同家族 2B 训、4B 跑；保留回退 Qwen2.5/Qwen3 |
| 12 | **成本/时间超预期** | DeepSeek 输出 ¥8/百万；当前 6s/轮、多段调用；工程 6–9 周 | 每月 API 账单超预算；每天维护时间挤占聊天 | 关 thinking、限制 evidence/tool 调用；每月预算 100–300 元；每周固定 2–3 小时工程；不追“每周上线” |
| 13 | **安全/依恋/隐私** | 越像“专属伙伴”，越需要边界；危机、自伤、排他话术必须有硬编码与人工出口 | 出现排他/威胁离开/危机未转人工 | 危机路径硬编码（修 bug）；AI 身份透明；不制造排他；数据本地训练、不上传；敏感内容不进训练集 |

**结论性提醒**：上面 13 个风险里，只有 #5/#6 是“模型/训练”问题；#1/#2/#3/#8/#9 是数据与评测问题；#4/#7/#10/#11 是工程问题。**预算和时间应该按这个比例分配。**

## 7. 不推荐的做法（反模式）

1. 一上来就 7B/QLoRA/每周训练：6GB 装不下，样本不够，评测没有。
2. 把“最终回复”当小模型训练目标：小模型会变成大模型的劣质影子。
3. 用隐式反馈直接当正负标签：会把“话多/讨好/纠缠”优化上去。
4. 用绝对点赞做唯一信号：现有 6:0 已经证明会坍塌。
5. 把“内心独白”当事实写进 prompt/记忆：会诱导大模型引用它，污染 A/C 分层。
6. 让 inner 同步阻塞主链：现状 6s 已经够慢，必须并行/缓存/降级。
7. 在 P0 未修时接微信真实流量：危机崩溃是信任级事故。
8. 让训练集混入微信真人隐私聊天：只训练“你↔AI”的对话；微信侧只做记忆/上下文，不做训练语料。
9. 每周覆盖旧 adapter：版本化，保留回滚；每次只改一个变量。
10. 把“涌现”当验收标准：无法度量；用“盲评更想继续聊 + 不发散 + 不越界”替代。

## 8. 需要你拍板的 8 个问题（每个都给建议）

1. **目标排序**：体验优先 / 科学验证优先 / 成本优先？
   → 建议：**可验证的体验优先**（盲评当唯一裁判），成本第二。
2. **是否接受前 6–8 周不训模型，只攒数据/建评测？**
   → 建议：**接受**；否则 LoRA 只是自嗨。
3. **反馈交互是否改成“同题双版盲选 + 少量显式标签”？**
   → 建议：**改**；现有三档 6:0 已失效。
4. **训练算力**：本机 2B（免费、慢、6GB）还是云 GPU（几元/次，可做 4B）？
   → 建议：**本地 2B 为主，云卡只做 4B 实验/smoke**。
5. **模型**：Qwen3.5-2B 训 / 4B 跑（推荐），还是回到 Qwen2.5/Qwen3（更稳但旧）？
   → 建议：**Qwen3.5 家族**；2B 训、4B 跑；留 Qwen2.5 回退方案。
6. **数据边界**：只训练“你↔AI”对话（推荐），还是也纳入微信真人聊天？
   → 建议：**只训练你↔AI**；微信聊天只做记忆/上下文，不入训练集。
7. **重构方式**：增量改造 `selflearn`（快但债务保留）还是新写 `agi/hybrid` 并行 + 影子切换（稳，推荐）？
   → 建议：**新包并行 + shadow/canary**；旧包保留 fallback，不一次性删。
8. **投入节奏**：每天能聊多久、每周能花多少时间标注/工程？（决定第一次 LoRA 是 6 周还是 12 周）
   → 建议：先按“每天 30 分钟 + 每周 2–3 小时工程/标注”排期；不够就把“每周微调”改成“每月 adapter”。

## 9. 最终判断

- **可行吗？** 有条件可行。技术栈在本机可落地（2B LoRA + 4B 推理，Windows 原生），但需要 py312、Ollama、独立训练进程；4B 微调必须云。
- **值得做吗？** 值得做“可证伪的混合路线”，**不值得**按“每周微调、不需要数据、性格自动涌现”的原始预期直接开工。
- **先做什么？** 不是 LoRA，而是：**修 P0 → 建尺子 → 记全 `inner_state/反馈/版本` → 用 3 臂 A/B 证明“状态注入”有增益 → 再进入 LoRA**。
- **什么时候能看到“它长出了性格”？** 按每天 30 分钟、每周盲评：**6–8 周第一次可测的 adapter，10–12 周才可能看出稳定差异**；如果 6 周内“状态注入”都赢不了 no-inner，那么 LoRA 也不会救。
- **最大的风险不是 6GB 显卡，而是“用不可信的数字做每周决策”。** 先把评测做成硬门槛，再让模型学习。

## 零、结论

**用得上，而且改变了「先在哪实现」的答案。**

分三层用法：

| 层次 | 能用吗 | 说明 |
|---|---|---|
| **代码直接搬** | ❌ | 它是 JS/DSH/QQ，AGI 是 Python/微信，协议与语言都不同 |
| **设计与契约** | ✅ 高价值 | 注入点、状态通道、记忆分类、评估协议，全都可以移植 |
| **工程经验与风险清单** | ✅ 直接吸收 | 隐式信号不能当标签、冻结 eval、replay、隐私红线——比 16 写得更狠 |

**最重要的发现：它印证了 15 的四个判断，并且补上了 AGI 最缺的东西——一个已经在跑的运行时。**
反过来，AGI 的 09/10 正好补上 QQ 缺的东西——短时情绪状态。**两边是互补的，不是二选一。**

## 一、核实：这些声明是真的吗

不是转述，我抽查了代码。三个关键点全部属实：

| 声明 | 核实结果 |
|---|---|
| 注入管线 `buildWakePromptV2` 可挂新段 | ✅ `bridge.js:10293`，拼接在 `10346`，一行 `+ innerLine` 即可 |
| v2 模式「AI 文本不自动发 QQ」，天然是独白 | ✅ `agent.cordis.yml:31`：「文本输出只是思考，【不会自动发送到 QQ】」 |
| 记忆三件套 `activeTopic/pendingThought/memberImpression` | ✅ `mcp-snowluma-safe.js:907`，`formatMemoryV2` 在 `bridge.js:8802` |

**一处需要澄清**：`bridge.js:10324` 确实已经有一个 `【此刻状态】` 段，但它是**运营状态**（未读数、最近一条消息、上次发言距今），**不是情绪状态**。
所以落地包说「没有此刻心情这种会过期的短状态」是准确的——两者不能混为一谈。

**结论：这份包的事实基础可信，可以按它规划。**

## 三、映射：16 的每个零件 → QQ 侧现状

| 16 的零件 | QQ 侧 | 复用度 | 怎么用 |

| 数据落盘 | ✅ `state/*.jsonl` | 90% | 加 `turns.jsonl` 归档 |
| **黄金集 / 四条件消融**（§8） | ❌ 没有 | **0%** | **必须新建**，用 16 的四条件 |

**真正要新建的只有 4 样：状态引擎、黄金集、成长日志、状态落盘。** 这与落地包自己的判断一致（3 个零件 + 评估）。

## 四、它比 16 更好的 6 处（吸收进 16）

| # | 它的做法 | 为什么比我写得好 |
|---|---|---|
| 1 | **隐式信号只记不训** | 05 §零 把「训练目标和人格目标相反」讲透了：用「对话延续」当正样本，会训出一个话痨客服，正好毁掉角色卡里「允许潜水、不必有求必应」的设计 |
| 2 | **冻结基准 eval set（50 条固定上下文）** | 单靠黄金集不够；固定基准专门检测「有没有变得不像原来那个它」——比我 16 的 7 天一致性测试更直接 |
| 3 | **每轮从 base 重训 + 混 30–50% replay** | 我 16 只写了「混 30% 通用数据」，漏了 replay 和「不要连续 merge 十几个 adapter」 |
| 4 | **inner 不写具体人名** | 05 §一.5 举的例子是真的会出社交事故：写了「对阿澈不爽」，下一轮说漏嘴。我 16 完全没这条 |
| 5 | **6 小时衰减 + 允许推翻** | 状态不是越新越真；旧情绪要降级成「很久以前的状态，不用太当真」，这个提示词细节比我写得好 |
| 6 | **控制台先做、QQ 侧后做** | 群聊加 👍/👎 会被群友看见、还得处理乱点；控制台补标才是对的 |

## 五、它比 16 弱的 5 处（别照抄）

| # | 问题 | 为什么是问题 | 改成 |
|---|---|---|---|
| 1 | **G2 判据「B 赢 12/20」太弱** | 12/20 = 60%，95% CI ≈ 36%–81%，跨 50%，统计上等于没判据 | 用 16 的 100 context + Wilson 区间；若坚持 20 组，至少 **17/20** |
| 2 | **inner 存在 `social-v2.json` 里，没有事件日志** | 无法回放、无法审计、改坏了没法比较前后 | 用 16 的 `inner_state` 追加表（保留 `prev_state_id`） |
| 3 | **「半天完成」只对 QQ 成立** | AGI 没有代码，把 QQ 工时套到 AGI 会严重低估 | 两个项目分开估时，见 §八 |
| 4 | **大模型自写 inner ≠ 小模型嗓音** | 前者是自我报告（准但贵），后者是独立渲染（便宜但可能噪声）；混着评会得出错误结论 | 评估分三层：A 无 inner / B 大模型写 / C 小模型写，分别比 |
| 5 | **它复用 OneBot/QQ 协议** | 代码依赖 QQ 侧，AGI 的微信/本地链路用不上 | 只复用**契约**（InnerState JSON、注入块、评估协议），代码各写各的 |

## 六、最重要的互补（这份包最大的价值）

```
QQ 缺什么                          AGI 有什么
─────────────────────            ─────────────────────
短时情绪状态（01:80 自认）    ←    09：五维情绪 + 衰减 + 边界梯子
信任/记仇（无）               ←    10：Mood / Trust / Memory 三层
                              ←    03：两段式生成 + 校验器
                              ←    02：证据链七道闸门

QQ 有什么                          AGI 缺什么
─────────────────────            ─────────────────────
运行时（Bridge + DSH）        →    一行代码都没有
注入管线 buildWakePromptV2    →    prompt 组装未实现
记忆三件套                    →    记忆层未实现
成本账本 + 安全边界 + 回归测试 →    全都没有
```

一句话：**AGI 出规格，QQ 出运行时；先在 QQ 验证，再把契约搬回 AGI。**

这也回答了 16 里悬着的问题——「4060 上跑不跑得动」在第一步根本不重要，因为**第一步（验证注入有没有用）不需要 GPU**。

## 七、两条实施路线

### 路线 A · QQ 优先（推荐）

| 阶段 | 内容 | 工时 |
|---|---|---|
| Step 0 | 把 09 的五维状态塞进 `inner`（不是只有 mood 一句话），落盘 + 注入 + 控制台卡片 | 1 天 |
| Step 1 | 控制台打分（好/一般/差 + 备注） | 半天 |
| 观察期 | 只攒数据，不改行为 | 2 周 |
| Step 2 | `turns.jsonl` 归档 + 导出 | 1 天 |
| Step 3 | 四条件消融（QQ 版，100 context） | 1–2 天 |
| G2 | 判据见 16 §8.3（不是 12/20） | — |

**优点**：3 天内就能看到「它记得上次心情」；风险低（都可回滚）。
**风险**：真实群聊隐私（05 §三）；QQ 不是最终形态，做完要回迁。

### 路线 B · AGI 优先

按 16 走 4 周。但前置是 Python 运行时（记忆、检索、prompt 组装）都不存在，等于先做 00–05 的 M0/M1 四个月，再回来做嗓音层。

**优点**：符合 00–14 的长期设计。
**缺点**：4 周内看不到任何结果，也验证不了「独白到底有没有用」这个最关键的问题。

### 折中（我建议）

1. 在 QQ 上做 **2 周实验**，只回答一个问题：**注入状态有没有让回复更好**（16 §8 的四条件，QQ 版）。
2. 同时把契约冻结成 `voice-contract.md`：InnerState JSON、`<inner_state>` 注入块、评估协议、判据。
3. 实验通过 → 按契约在 AGI 实现（此时 09/10 的状态机已有现成实现可抄）；不通过 → 省下 AGI 的 4 周。

**这就是「先做实验，再建系统」——和 08 文档 E0 的方法论一致。**

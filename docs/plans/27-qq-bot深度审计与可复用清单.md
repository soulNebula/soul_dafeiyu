## 二、最该先修的其实是**我们自己**（比接灵魂模型更紧急）

审计时把 `wx_box/agi/data/wechat/gateway.log` 拉出来算了（我复核过）：

|---|---|---|

**根因**：`agi/wechat_gateway/config.py` 里 `proactive_interval_min_s: 30 / max_s: 300`（=30 秒到 5 分钟一次）。

> 当前 `proactive_enabled` 已是 `False`，暂时不会触发；但一旦打开就会重现。
> **修这一项对"人格稳定感"的提升，可能大于把灵魂模型接进 chat**——没有人愿意 3 分钟收到一次"你在干嘛"。

## 四、明确不要抄

1. **纯 QQ 适配层**：SnowLuma/OneBot、CQ 转义、禁 @all、拍一拍、群公告/踢人、emoji_id CDN、空格分句 + `[SILENT]`、`forward.js` 合并转发
2. **四模式状态机**（chat/closed-agent/reserved/reserved2）= 四份人格分裂；我们只需 interactive / quiet 两档
3. **`closed-agent`**（QQ 私聊远程操控本机 + 完整工具）——纯风险
4. **burst 连发**（他们一口气 8 条）：微信同一对话框，46% 失败率会放大成半句话
5. **每轮注入 6000 字符人格卡**（≈4–6k token）：他们必须每轮注入是因为 QQ 会话按需重建；我们是长会话，人格卡只需首轮 + 重大变更
6. **黑话自动联网研究**（默认 true 会把群聊关键词发给搜索后端；数据出机）
7. **用"对话延续度"当正样本**：与"允许沉默"直接对冲，会训出话痨客服；隐式信号只记不训
8. **JSONL 无限追加账本**（我们有 SQLite）
9. **把 190 个 API 全量暴露**（只暴露 10 个安全子集）
10. **`session-router.mjs`**：623 行 + 353 行测试，**没有任何生产代码 import**（别以为是运行中的代码）；`config.example.json` 的 `maxInjectChars: 6000` 与代码默认 8000 冲突

## 五、他们踩过的坑（挑 6 条对我们有直接映射的）

| 他们的坑 | 我们的映射风险 |
|---|---|
| 上游字段断裂（`value.queues[<id>]` 从来不存在）→ 每次退役抛错、日志只有一行警告 | 我们 `turns`/`pairs`/`inner_states` 表结构变更时，**旧代码静默读空** |
| 静默失败三连（good 恒 null / hook 永不触发 / restrict 只看分子） | 小模型"端口通但输出空"；proactive 闸门"算出来但没发" |
| 双实例 + 旧快照覆盖（`Win32_Process.CommandLine` 相对路径匹配不上 → 两实例互相覆盖 social-v2.json） | 我们 gateway 54 次重启 / 18.3h，**必须查是否有双实例** |

| "连上了≠收得到"，且会被误报成自己的 bug | 微信网关"进程活着但收不到消息" |
| 权限收紧后写不进沙箱（R10，有意取舍），**绝不能用继承 ACL"修好"** | 我们 `harden_acl.py` 同类陷阱 |

```
                        ↓（这比接灵魂模型更影响"像不像人"）

                        ↓

                        ↓
P2（3–5 天）             黑话闭环 + 表情包认知层 + 成本账本（prices+ledger 骨架）+ 人格卡分节
                        ↓

```

**他们两条明确反对、我们要听的**：
1. **不要做自动 A/B 分流**（一天几十条样本，统计上测不出显著差异，人工看 100 条更准）
2. **不要"按节奏训练"**（有节奏没评估 = 每周随机调整一次人格；真正该保持的是每周评估，有明确提升才替换）

### 8.3 剩余风险与 backlog

1. **未做真机验证**：以上"P0 后"数字来自单测与模拟；真实发送需用户同意后开 `proactive_enabled` 观察 4–6 小时。
2. **wxauto4 的 topui 根因未修**（第三方库内部），我们只是把"致命"降级为"确认后继续/否则 draft"；长期建议升级 wxauto4 或发送前主动关资料卡。
3. **fallback auto 模式 `verified=False` 仍会被当送达**（默认关闭）——见 backlog `task-22`。
4. **`/status` 的 sent 计数**仍把 clipboard/planned 算成功（指标层，不影响主动链失败率）——见 `task-22`。
5. **`out.drafts` 混合**"失败落草稿"与"confirm 人工草稿"，统计需用 `send_failed` 区分。

### 8.4 真机验收方案（待用户点头）

把 `agi/data/wechat/config.json` 的 `proactive_enabled` 置 `true`（`dry_run` 保持当前值），目标联系人用「文件传输助手」自测，跑 4–6 小时，检查：
1. 间隔分布是否落在 1–120 分钟；
2. 发送条数 ÷ 检查轮数是否 ≈0.6；
3. 是否出现重复/高相似文本（应被 1800s 去重挡住）；
4. `proactive_send` 里 `status ∈ {failed, draft(send_failed), clipboard}` 的比例（失败率）；
5. 23:00–08:00 是否有发送（应无）；
6. `gateway_stale` 是否在真实空闲期出现（不应频繁误报）。

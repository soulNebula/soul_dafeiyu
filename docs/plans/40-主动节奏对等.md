# 40 · 主动节奏对等（P16-B）

> 用户诉求（2026-10-26）：「主动发消息的条数要和用户主动发给它的条数相近，而不是我多他少」。
> 旧节奏是固定概率 0.5–0.6、间隔 60–7200 秒随机；用户聊得多时它明显偏少。
> 本任务让主动消息的「量」跟随用户近 7 天的主动量自适应，但保留静默/上限/无回应保护。

## 1. 模块与数据口径

新模块 `agi/selflearn/pacing.py`（只读，不写配置、不发消息）：

| 指标 | 来源 | 说明 |
| --- | --- | --- |
| `user_initiated` | 联系人 memory 库 `messages` 表 `role='user'`，近 7 天 | 用户发来的消息（被动回复也是用户先开口）；按联系人隔离 |
| `agent_proactive` | `proactive_events` 表 `status='sent'` 且 intent `kind != 'reply'`，近 7 天 | 它主动发出的条数；表缺 kind 列时按 status 统计 |
| 兜底 | `git` 不管的 `agi/data/wechat/gateway.log` 的 `proactive_send` 事件 | 仅当库/表不存在时用；**两者只取其一**，避免重复计数 |
| `today_agent_proactive` | 同上，`ts >= 本地当天 0 点` | 日上限用 |
| `unanswered_streak` | 最近连续 `proactive_events.response IS NULL` 的条数 | 连续 3 条无回应 → 保守 |
| `ratio` | `agent_proactive / user_initiated` | 双方都 0 → 1.0（平局）；用户 0 但它发过 → 视为偏高 |
| `deficit` | `user_initiated - agent_proactive` | 正数 = 它发少了 |

`balance(path, now, contact=..., log_path=...)` 返回上述统计 + `suggested{probability, interval_min_s, interval_max_s, send, reason}`（按默认参数算的基线建议；worker 用 `adjust()` 结合真实 config 再算）。

## 2. adjust 规则（纯函数）

`adjust(config, balance, now=None, stopped=False)`：目标比例 `target_ratio`（默认 1.0），容差 `tolerance`（默认 ±25%）。

判定顺序（先命中先返回）：

1. **STOP / `stop` 开关** → `send=False, reason=stopped`（不发）
2. **夜间静默**（`quiet_hours`，如 [22,9]，跨零点；`proactive_override_quiet=true` 可覆盖）→ `send=False, reason=quiet_hours`
3. **当天主动已达 `pacing_daily_cap`（默认 12）** → `send=False, reason=daily_cap`
4. **连续 ≥3 条无回应** → 保守：概率 ≤0.2、间隔 ≥3600s（`reason=no_response`），仍可发
5. **ratio < target×(1-tolerance)**（默认 <0.75，它发少了）：
   - 概率 = 当前区间中点 +0.15（上限 0.9；若已 ≥0.9 则保持）
   - 间隔 ×0.6（下限 `pacing_min_interval_s`=1200s）
6. **ratio > target×(1+tolerance)**（默认 >1.25，它发多了）：
   - 概率 = 中点 −0.15（下限 0.2）
   - 间隔 ×1.5
7. 容差内 → 保持原概率区间中点与配置间隔

返回值（只用于本轮调度，**不改写用户 config 文件**）：

```json
{"applied": true, "send": true, "reason": "under|over|within|no_response|quiet_hours|stopped|daily_cap|pacing_disabled",
 "probability": 0.7, "interval_min_s": 2160, "interval_max_s": 4320,
 "ratio": 0.058, "deficit": 65, "target_ratio": 1.0,
 "today_agent_proactive": 0, "unanswered_streak": 0,
 "base": {"probability": 0.55, "interval_min_s": 3600, "interval_max_s": 7200}}
```

## 3. 配置参数（`agi/wechat_gateway/config.py` DEFAULTS，可被 `agi/data/wechat/config.json` 覆盖）

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `pacing_enabled` | `true` | 总开关；`false` 时 worker 完全不调用 pacing，回退旧固定概率/间隔 |
| `pacing_target_ratio` | `1.0` | 目标 `agent_proactive / user_initiated` |
| `pacing_tolerance` | `0.25` | 容差（±25% 内不调整） |
| `pacing_daily_cap` | `12` | 每天主动条数硬上限（到顶不发） |
| `pacing_min_interval_s` | `1200` | 调整后间隔下限（20 分钟） |

静默时段继续用 `quiet_hours`；STOP 仍走既有 STOP 文件/开关。

## 4. 接线（`agi/wechat_gateway/proactive_worker.py`）

- 每轮 `run_cycle` 的**每个联系人概率闸门之前**：
  1. `balance(contact_db, now, contact, log_path)` 统计近 7 天对等度；
  2. `adjust(gateway.cfg, balance, now, stopped=cfg.stop)` 得本轮建议；
  3. `send=False` → 记 `skipped{reason:"pacing:quiet_hours|daily_cap|stopped"}`，**不查库、不调 LLM**，本轮跳过该联系人；
  4. `send=True` → 用建议 `probability` 替代旧 `_probability()` 掷骰；把建议区间放进 `out["pacing_suggested"]`，供 `next_interval()` 使用；
  5. 记 `pacing_adjusted` 事件（contact/ratio/deficit/user/agent/today/streak/probability/interval/目标比例）。
- `next_interval(last_outcome=...)`：若 outcome 带 `pacing_suggested`，本轮下次等待在该建议区间内均匀随机（否则用 `proactive_interval_min_s/max_s`）。
- 只影响调度，不改内容生成/发送实现；不改写 config 文件。

## 6. 如何关闭 / 调参

- 关闭：`agi/data/wechat/config.json` 加 `"pacing_enabled": false`（热加载，下一轮 cycle 生效），或控制台改配置后保存。
- 调目标：`pacing_target_ratio`（如 1.0）、`pacing_tolerance`（0.25）、`pacing_daily_cap`（12）、`pacing_min_interval_s`（1200）。
- 只对主动消息生效；被动回复、草稿/确认模式、内容闸门、去重、熔断、静默/STOP 全部不受影响。

## 7. 风险与上限

- **日上限**：`pacing_daily_cap=12`，即使 ratio 极低也不会超过（按当天已发送事件计数）。
- **夜间**：`quiet_hours` 内不发（避免凌晨骚扰）；`proactive_override_quiet` 仍可临时覆盖。
- **连续无回应**：≥3 条未回应 → 概率 ≤0.2、间隔 ≥1h，避免「舔狗式刷屏」。
- **样本噪声**：7 天窗口内用户消息少时 ratio 抖动大；双方都 0 时按 1.0 平局处理，不做动作。
- **缓存/延迟**：7 天滚动统计，节奏调整有滞后；`proactive_events` 缺失时回退 gateway.log（可能与库有少量差异，但只取其一不重复）。
- **可观测**：`gateway.log`/`/status` 的 `pacing_adjusted` 事件带比例、差额、建议值，便于验收与回滚。
- 本次未改内容生成、未改发送实现、未改用户配置。

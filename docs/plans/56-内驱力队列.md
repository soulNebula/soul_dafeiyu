# 56 · 内驱力队列（urges）

用户批准的方向 ②：**让主动不是纯概率/骰子，而是攒着一个「想跟他说 / 想分享」的欲望**，
有强度、会衰减，合适时机优先说；被回应就满足，被忽略就慢慢凉。

本任务（P34）分两段落地：
- **已完成（不冲突部分）**：`agi/selflearn/urges.py` 队列模块 + `surf.py` 冲浪结束触发 +
  测试 + 本文件；
- **待接线（等 P33 drive 落地 / 冲突窗口）**：`proactive_worker` 优先发 urges、
  入站回复 satisfy、`GET /api/urges/status`；interests/未来事件/心情的触发点
  （chat.py 正被 P28 改，避开）。

---

## 1. 为什么

现在的主动消息 = pacing（条数比例）+ initiative（关系/心情的 drive）+ 随机概率。
缺的是「**她自己的想要**」：有些东西她刷到、想到、好奇，不是立刻要发，而是攒着，
等到合适时机说；说完被回应会满足，没人理就慢慢凉。urges 就是这层「欲望缓冲区」，
同时给主动消息一个**可解释的原因**（控制台能看到她此刻最想说什么）。

## 2. 数据结构与 kind/半衰期

memory 库新表 `urges`（**惰性创建**：第一次调用时 `CREATE TABLE IF NOT EXISTS`，
失败静默，不阻断主链）：

| 列 | 说明 |
| --- | --- |
| `id` | `U-<sha1>` |
| `contact` | 联系人（缺省=库名 stem） |
| `kind` | 见下表 |
| `topic` | 主题/关键词/事件 |
| `payload_json` | 上下文（冲浪摘要、来源、事件原文、心情值、`available_at`…） |
| `intensity` | 0–1 强度 |
| `created_at` / `updated_at` | 创建/最近衰减时间 |
| `attempts` / `last_attempt_at` | 试过几次（spend 时 +1） |
| `status` | `active` / `spent` / `dropped` |
| `ref_json` | 溯源（surf_session 等） |

| kind | 含义 | 半衰期 |
| --- | --- | --- |
| `share_find` | 冲浪/新闻/视频里的发现，想分享 | **3h** |
| `share_thought` | 她自己想到的（兴趣在升温） | **1.5h** |
| `ask_about` | 好奇想问的 | **2h** |
| `progress_check` | 追问用户之前提过的进度（面试/考试…） | **12h**（且推入后 24h 才允许触发） |
| `light` | 就想找他说一句 | **0.75h** |

强度公式：`intensity *= 0.5 ** (elapsed_hours / half_life_hours)`（增量式，反复调用不会重复衰减；
`progress_check` 在 `available_at` 前不衰减）。

## 3. push 规则（防刷屏）

`push(path, kind, topic, payload=None, intensity=0.6)`：

1. **clamp** 强度到 [0,1]；未知 kind 直接忽略（返回 None）；
2. **去重**：同 contact+kind+topic 且 24h 内已有 active → 不新增，强度取
   `max(旧, 新) + 0.1`（越攒越想）；
3. **同一天同类最多 3 次**（按本地日期；Windows 1970 附近时间戳有兼容兜底）；
4. **队列上限 8**：满了丢**最弱**一条；新欲望比最弱还弱 → 不进队；
5. 全部 try/except：坏路径/坏数据只返回 None/0，不抛异常。

生命周期：

- `decay(path, now)`：按 kind 半衰期衰减（增量更新 `updated_at`）；
- `top(path, now, min_intensity=0.35)`：先 decay，返回最强且**当前可用**的一条
  （progress_check 未到 `available_at` 会被跳过；含 payload/ref/age）；
- `spend(path, urge_id)`：发送成功 → `spent`、attempts+1；
- `satisfy(path, contact)`：用户回复 → 该联系人所有 active 强度 ×0.3 并标 `spent`；
- `cleanup(path, now)`：`intensity<0.05` 或 24h 未用 → `dropped`
  （progress_check 在可用后 48h 才清）；
- `list_active/status`：给控制台/调试看队列前 5 条。

## 5. 与 pacing / initiative 的优先级（待接线设计）

每轮 worker：

1. `urges.decay()` + `urges.cleanup()`；
2. 若 `initiative.drive ≥ 0.35` 且不在静默/冷却/日上限 → `urges.top(min=0.35)`；
3. 有 top → **优先发这条欲望**（share_find 用素材摘要+自己的看法；ask_about/progress_check
   用事件；light 用短句），发送成功 `spend`，失败 `intensity*=0.5` 不 spend；
4. 无 top 或 drive 不允许 → 回退现有随机/pacing 逻辑；
5. 用户入站回复 → `satisfy(contact)`；
6. 日志 `urge_fired`（kind/topic/intensity/attempts）；开关 `urges_enabled`（默认 true，
   env `URGES_ENABLED` 优先）。

**优先级原则**：urges 只是「候选内容源」，不突破 pacing 的日上限/静默时段/无回应冷却；
drive 决定「今天多想发」，urges 决定「发什么」。两者都满足才发。

队列清空（下一轮重新攒）。

## 8. 隐私 / 失败策略 / 开关

- 数据只在本机 memory 库（按联系人隔离）；payload 含用户提过的事件原文，仅本机用；
- 所有函数失败静默：urges 挂掉不影响冲浪/聊天/主动消息主链；
- 开关：`urges_enabled`（默认 true；env `URGES_ENABLED` 可覆盖）；
- 清理：强度凉透/超龄自动 dropped，队列最多 8 条，不会无限膨胀。

## F1 · 测试会写生产配置（P0，建议不延后）

**现状（实测）**
- `python -m pytest agi/tests -q` → **2000 passed / 2 failed / 1 skipped**（963s）；
- 失败两条单独重跑 → 18 passed，说明是跨用例污染；
- 测试窗口内 `agi/data/wechat/config.json` mtime 变为 `03:22:18`、根 `config.json` mtime 变为 `03:24:05`（内容等价，但文件被重写）。

**根因链**
1. `Gateway.__init__`（`agi/wechat_gateway/server.py:177`）`config_path` 默认 = 生产 `config.CONFIG_PATH`，并记录 `_cfg_mtime`；
2. `_send()` 首行 `reload_config_now()`（`server.py:1261`）——mtime 变化即热重载；
3. 某个用例把配置写回生产路径（`server.py:616` `cfg.save_atomic(payload, self.config_path)`）；
4. `agi/tests/conftest.py` 已隔离 `contact_db` 与 STOP 路径，**唯独没隔离 `CONFIG_PATH`**；
5. 于是「先构造的 Gateway 在下一次 `_send` 时被磁盘上的生产配置覆盖」→ 注入的 `allowed_contacts=["x"]` 被换成生产白名单 → `error: not_allowed`。

**为什么建议不延后**
- 根 `config.json` 含 `db_keys`（实测 16 条）、`image_aes_key`、`image_xor_key`；本次内容恰好等价是运气，
  任何新增用例一旦写这些字段，就是**静默丢失解密密钥**；
- 后续要做 CI，而"2003 条里随机翻红"的套件进 CI = 红绿灯不可信，正好抵消本轮整改的核心成果；
- 成本约 5 行。

**修法**
在 `agi/tests/conftest.py` 增加 autouse fixture，与既有 STOP 隔离同一手法：

```python
@pytest.fixture(autouse=True)
def _isolate_gateway_config(tmp_path, monkeypatch):
    from agi.wechat_gateway import config as gw_config
    monkeypatch.setattr(gw_config, "CONFIG_PATH", tmp_path / "config.json")
```

并确认 `Gateway.config_path` 默认值在**实例化时**读取模块属性（而非模块级常量快照），
否则已构造实例仍指向生产路径。

**验证**
- `pytest agi/tests -q` 连续两次全绿；
- 跑前跑后 `stat config.json agi/data/wechat/config.json` 的 mtime 不变；
- 建议把"跑完不改生产文件"做成一条断言/CI 步骤。

## F2 · 空白名单 = 全放行（P1，开源前）

**现状**：`server.py:1275-1279`

```python
allowed = [str(x).strip() for x in (self.cfg.get("allowed_contacts") or []) if str(x).strip()]
if allowed and str(contact or "").strip() not in allowed:
```

空列表直接跳过校验；而新装默认 `allowed_contacts: []`。
与 `docs/风控与合规说明.md` §一/§二「发送目标受 allowed_contacts 白名单约束」的表述冲突。

**修法（二选一）**
- fail-closed：`if not allowed: return blocked("no_allowlist")`；
- 或首启向导强制填至少一个联系人，未填则不允许 `enabled=true`。

**验证**：单测覆盖 `allowed_contacts=[]` 时 `_send` 返回 `blocked`。

## F8 · 窗口级兜底发送 + `send_mode=auto`（P0，新增，2026-10-28 03:41 实测）

**现状（复检时实测，非文档推断）**

`agi/data/wechat/config.json`（mtime 03:41）实际值：

| 键 | 实测值 |
|---|---|
| `send_mode` | **auto** |
| `dry_run` | false |
| `fallback_enabled` | **true** |
| `fallback_mode` | **auto** |
| `fallback_send_mode` | contact |
| `allowed_contacts` | 2 个 |

而 `docs/STATUS.md` §6 第 3 条同时记载：
- wxauto4 41.1.7 的 UIA 绑定在本机**已失效**（`WeChat()` 报「未找到已登录的客户端主窗口」）；
- 因此启用了窗口级兜底 `win_send.send_to_contact()`。

**风险叠加**
`win_send.py:101-108` 明确写：*"坐标按窗口尺寸比例计算…**无法校验会话名**，结果一律 `verified=False`"*。
即：兜底路径 = 点搜索框 → 粘贴联系人名 → 回车 → 点输入框 → 粘贴 → 回车，
**全程不确认最终打开的是哪个会话**。

当 UIA 主路径在本机恒失效时，意味着**所有发送都走这条无法校验目标的路径**，且 `send_mode=auto` 无人工确认。
潜在后果：搜索无结果时回车可能停留在上一个会话 → 消息发给错误的人。

**与既有声明冲突**
- `docs/STATUS.md` §6 第 3 条自己写「生产建议保持 `send_mode=confirm`」，但配置是 `auto`；
- `docs/风控与合规说明.md` 称"发送目标受 `allowed_contacts` 白名单约束"——
  白名单只约束**传入的 contact 字符串**，不约束**实际打开的会话**；
- 基线报告里称赞的「`ChatInfo()` 双验、会话名不符即 fail-closed」在兜底路径下**不成立**。

**立即动作（1 分钟内可做）**
1. `send_mode=auto` → `confirm`（恢复人工批准）；
2. `fallback_mode=auto` → `manual`（只落剪贴板，不自动粘贴回车），或 `fallback_enabled=false`；
3. 在 wxauto4 UIA 修好之前，不要把兜底设为 `auto`。

**根治方向**
- 兜底发送前增加目标校验：发送后用截图/OCR 复核会话标题与 contact 是否一致，不一致即中止并落草稿；
- 或兜底前先断言"搜索框回车后标题栏文本 == contact"（`win.capture` + OCR 已有能力，见 `wx_core/ocr.py`）；
- 把"发送目标可验证"做成 `sendclass` 的一个硬等级，`verified=false` 的发送默认不自动启用。

### F8 附：wxauto4 为何失效（2026-10-28 04:20 定位）

**不是 wxauto4 的 bug，也不是配置/依赖问题。** 实测：

| 客户端 | 桌面顶层元素 | 微信主窗口子树 |
|---|---|---|
| .NET `UIAutomationClient`（PowerShell） | **6** | **164**（`mmui::MainWindow` → `mmui::MainView` / `mmui::MainTabBar` / 按钮名齐全） |
| comtypes 1.4.11（venv） | **0** | **0** |
| `wxauto4.uia`（内置 ctypes uiautomation） | **0** | **0** |

即：**任何 Python UIA 客户端在本机都只拿到 HWND 层信息，拿不到应用 provider 的子树**；
.NET 客户端同机、同 DLL、同会话下完全正常。wxauto4 因此判定"未找到已登录的主窗口"。

已排除：Job 对象/UI 限制（`in_job=False`、`ui_restrictions=0x0`）、STA vs MTA（两种都试）、
启动上下文（bash 与 pwsh 启动结果一致）、环境注入（`python -I` 一致）、
DLL 劫持（加载的是 `C:\Windows\System32\uiautomationcore.dll`）、位数（均 64-bit）、venv 重建。

**因此**：重装 wxauto4、升降级 comtypes、重建 venv 都不会修好——不要再在这条路上投入。

**替代方案（推荐）**：改用 **.NET UIA** 作为发送通道——
新增 `tools/uia_send.ps1`（PowerShell + `UIAutomationClient`），由 `send_cli.py` 以子进程调用；
因为 .NET 能看到完整元素树，可**先读会话标题校验再发送**，正好一并根治本条的"无法校验会话"问题。

## 2. 步骤与实测结果

### 2.1 803 建 bot

```bash
curl -X POST http://127.0.0.1:803/api/bots -H "X-Admin-Token: <token>" \
  -H "Content-Type: application/json" \
  -d '{"bot_id":"v1-accept","name":"V1 Acceptance","plan":"cloud",
       "soul_provider":"cloud","password":"v1accept123"}'
```

- 结果：`{"ok": true, "bot": {..., "has_password": true, "secrets_saved": true}}`
- 产物：`bots/v1-accept/{bot.json,config/wechat.json,secrets/keys.json,secrets/auth.json,db/selflearn,logs,…}`
- 密码只存 PBKDF2 哈希（`secrets/auth.json`）；密钥 `secrets/keys.json` 为 DPAPI 加密。

### 2.2 加载（分阶段校验，不启动服务）

`POST /api/bots/v1-accept/load` → `ok: true, progress: 100`，7 个阶段全绿：
目录 / bot.json / 数据库目录 / 密钥文件 / 网关配置 / 云端灵魂模型 / 802 端口（提示"已在运行，将复用"）。

### 2.3 自检

`GET /api/selfcheck?bot_id=v1-accept` → `ok: true`，检查项：
`803`、`port_801`、`port_802`、`bot:v1-accept`、`bot/<各阶段>`、`802 登录密码` 全通过；
快照落 `logs/selfcheck-v1-accept-<ts>.json`（实测 `logs/selfcheck-v1-accept-1793534506.json`）。

可选模型连通（`models=1` 或 803 页面「测模型」）：当前 bot 未填 key 时
实测返回 `{"ok": false, "checks":[{"purpose":"chat","error":"all_backends_failed: api=unavailable",
"hint":"未填写 API key：在 803 新建/保存 bot 时填DeepSeek key"}]}` —— **失败原因可操作，
不误报成"模型坏了"**，也不回显任何密钥。

### 2.4 802 登录（bot 密码模式）

`launch` 前先手工在空闲端口验证一次（8122），再走 803 `launch`（8199）：

| 请求 | 结果 |
|---|---|
| `GET /login` | 200（登录页 1499 bytes） |
| `POST /api/auth/login {"password":"wrong"}` | **401**（失败限速生效） |
| `POST /api/auth/login {"password":"v1accept123"}` | 200 `{"ok": true}` + HttpOnly 会话 cookie |
| `GET /api/config`（带 cookie） | 200，返回 bot 包配置（非全局旧配置） |
| `GET /api/bili/display`（带 cookie） | 200 `{"show_danmaku": false, "show_comments": false}` |
| `GET /api/bili/repo/status`（带 cookie） | 200（旧插件凭证只读兼容，凭证值不回显） |

启动日志确认 bot 生效：`[802] bot=v1-accept soul=cloud chat_backend=api soul_backend=api`。

> 本 PR 顺手修了验收暴露的一个真实缺陷：新增的 B站接口原先只认 `X-Admin-Token`，
> bot 密码登录后页面拿 cookie 会被 401；现改为 **会话或 token 任一通过**（`request_authed`）。

### 2.5 开始运行（launch）

`POST /api/bots/v1-accept/launch?port=8199`（803 路由支持 `port` 参数，默认 802）→

```json
{"ok": true, "started": true, "pid": 23984,
 "url": "http://127.0.0.1:8199/", "log": "logs/console-8199.log"}
```

日志 `[802] bot=v1-accept …`，登录 200，`/api/bili/display` 200。验收后已停止该实例；
**未对活动端口 801/802 调用 launch**（802 在跑时 launch 会直接返回"已在运行，将复用"）。

## 3. 结论与遗留

- 全链路（803 建 bot → 加载 → 自检 → 802 登录 → launch 起 802）在真机通过，且不影响正在运行的 801/802；
- 自检覆盖：803/801/802 端口、bot 加载阶段、802 登录准备、可选模型通道；
  doc 64 §12 里的「微信进程/窗口探测」「识图冒烟」「801 `_reply` 冒烟」列为 V1 之后增强项
  （需要真实微信窗口/联网，不适合每次自检默认执行）；
- 真实消息发送（微信侧）不在本 PR 验收范围：801/802 活动实例按用户要求未重启，发送链路沿用既有已验收链路；
- 验收 bot `bots/v1-accept` 保留供复现，删除也不影响仓库（gitignore）。
